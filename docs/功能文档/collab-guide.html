协作是怎么跑起来的

用大白话讲清 Coda 里「多智能体协作」的工单机制、权限与流程 —— 不用懂代码也能看完。

一句话理解 三个词 一次任务怎么走 分支与回路 状态机 谁能干什么 工单的一生 工单里装了什么 成员看到什么 交接规则 中断与续接 随时找 CEO 防死循环 这次修了什么 你能做什么
一句话：你把一件事交给「小组长」，小组长不会自己埋头写完， 而是把它写成一张工单派给下游；活干完了，工单要一层层交回来，最后有人对你说一句结论。

这套机制要解决的核心问题只有一个：让「活干到哪了、干出了什么」永远有人看得见， 而且看的是结构化的结论，不是一大段聊天记录。

1. 先记住三个词

协作组

一个「编好队的小组」。里面画好了谁是谁的上级、谁审谁、谁能把活打回给谁。 就像一张组织架构图，图上的每条线都规定了活的流向。

智能体与岗位

智能体是一个具体的人设（比如「码农 · 小王」），背后选好了一个内核与网关。 岗位是它在这张图里站的位置（协调者 / 实施者 / 审查者），岗位决定了它能做什么、不能做什么。

工单

智能体之间唯一的交接物。它长得像一张任务卡：要干什么、验收标准是什么、 最后交回了什么结论、产出了哪些文件。智能体之间不传聊天记录，只传工单。

为什么只传工单？因为对话记录又长又乱、还容易互相污染。工单是「结论」，干净、可核对、可回放 —— 出了问题能一眼看出是哪一环没交清楚。

2. 一次任务怎么走

下边是一条典型链路。每一格都是一次真实调用（会花时间和钱），箭头就是「工单交给谁」。

👤 你「把登录页改成暗色主题」
▼
🧑‍💼 CEO（协调者）理解目标 → 不自己动手，把工单派给 CTO
▼ 派发
🧑‍🔧 CTO（协调者）把大任务拆成子工单 → 交给码农
▼ 拆子工单
👩‍💻 码农（实施者）真正动手干 → 提交结论 + 产出文件清单
▼ 提交
🔍 审查员（审查者）对照验收标准检查 → 通过 / 打回返工
▼ 通过
🧑‍🔧 CTO子工单收尾 → 汇总结论
▼ 收尾
🧑‍💼 CEO对你说一句结论：「已上线，改动在 theme.ts」
默认同一时刻只有一个人在干活。这是刻意的：串行推进才说得清「谁在等谁」， 取消、重试、排查也才有确定答案。预算里把「并行上限」调到 2 以上时， 同一次拆出的兄弟子工单（且分给不同岗位）可以同时开工，谁先干完谁先交； 同一个岗位永远一次只干一件事。

这条主链路上会用到六种动作，看懂这六个词就够用了：

动作大白话谁能用
delegate · handoff「这活我不做，转给你」，同一张工单换个人接着干协调者、实施者
delegate · split「这活太大，我拆成一张子工单给你」，拆的人负责最后汇总协调者、实施者
submit「干完了，这是我的结论和产出文件」实施者
review「我审了，通过 / 不通过（附原因）」审查者
done「这件事到此为止」，并写一句结论协调者
ask_user「这事得你拍板」，弹出可点选项只有入口智能体

出问题时还有两种：escalate（我搞不定，往上交）和 reject（这条路走不通，终止）。 连同转交、拆子工单、打回返工，下一节一起讲。

3. 分支与回路：工单不止一条直路

上面那条主链路只是一条最顺的路。真实干活时还会分叉、回头、卡住、甚至整条走不通 —— 这六种走法就是全部，认全了就不会再被「怎么又退回来了」搞懵。

➡️ 转交 handoff

  • 同一张工单换个人接着干，不新建工单
  • 新填的字段与原来的合并，不是推倒重来
  • 典型：CEO → CTO，同一件事往下传
  • 交出去的人不是撒手不管，它还在等这张工单的结果

🌿 拆子工单 split

  • 「这活太大，我拆成两张」：新建子工单，父工单原地等
  • 父工单变「等子工单」，子工单全通过后自动回到拆解者手里汇总
  • 典型：CTO 把「改登录页」拆成「改样式」+「接接口」
  • 最多拆 5 层；同一父工单下同名或近似同名的子工单最多 2 张

↩️ 打回返工 rework

  • 审查者判「不过」→ 工单变返工，附上具体审查意见
  • 默认退回最近提交的人；审查者也能指定退给谁（比如退回 CTO 重新拆解）
  • 改完重新提交，再走一轮审查
  • 返工轮次有上限（节点、边、运行预算三者取最小），超了就挂起喊你

⬆️ 上报 escalate

  • 「我搞不定」→ 工单变已上报，交回派活的那个人
  • 必须写清「卡在哪、需要什么」，然后一级一级往上报
  • 不许原样往下派：上抛件只能自己解决、继续往上、或交给用户
  • 到顶后变成一张问你「选哪个」的卡片；你答完，原工单接着跑

⛔ 否决 reject

  • 协调者 / 审查者判定这条路根本走不通 → 工单否决
  • 这条分支直接终止，错误往上抛给父工单的发起者
  • 它不是「返工」（改改还能救），而是「别再走这条了」

✅ 收尾 done

  • 确认完成，并写一句结论（空结论等于没交付）
  • 子工单收尾后父工单回到拆解者，由它决定继续还是收尾
  • 根工单收尾后交回入口智能体，由它向你汇报
整套机制里唯一的「回路」是审查 ⇄ 返工：有审查边就必须有退路，有退路就必须有来路。 普通「派发」边不许成环 —— 想循环，只能走这条显式的闭环，否则图校验直接不让你保存。

4. 状态机：一张工单怎么变

不用背，用的时候回来看这张表。左边是工单现在的状态，中间是谁在拿着它、能做什么， 右边是做完之后变成什么。表里没写的箭头就是不允许的 —— 引擎会直接拒绝，不会「试试看」。

状态谁持有能做的事做完变成
open 待领取 在就绪队列里排队，马上就会有人接手 派发 / 拆子工单 / 提交 / 收尾 / 上报 / 否决 被别人接手 → working；拆了子工单 → waiting_children
working 处理中 当前岗位正在干 派发 / 拆子工单 / 提交 / 收尾 / 上报 / 否决 交给审查 → review；没有审查者 → 直接 done
waiting_children 等子工单 拆解者暂时放手，等下面的活 什么都不做（由子工单推进） 子工单全部通过 → 自动回到拆解者手里（open），由它汇总
review 待审查 审查者 审查 / 上报 / 否决 通过 → done；不通过 → rework
rework 返工中 退回的那个岗位（默认是最近提交的人） 提交 / 收尾 / 派发 / 上报 / 否决 改完重新提交 → review；轮次超上限 → blocked
escalated 已上报 这张工单的发起人（逐级往上，到顶是入口智能体） 自己解决 / 继续上报 / 交给用户（不能往下派） 解决 → done；继续往上还是 escalated；入口发问 → blocked
blocked 卡住 在等你：回答了提问，或修掉了护栏 / 解析问题 你回答、点「重试」、改配置 你答完 / 修好 → 那张工单回到 open，进队列接着跑
done 完成 —（终态） 不动作；你在主会话里追问会重开根工单 只负责把结论和产出文件留给上游
rejected 否决 —（终态） 不动作 这条分支终止，错误抛给父工单的发起者

整个协作运行也有自己的状态，和工单状态是两回事：

运行状态大白话
running还在推进（可能中间有工单在等子工单）
waiting_user停下来了，在等你拍板或修东西
done所有工单收尾，入口智能体也已经向你汇报完
error某一步出了真错误，现场保留，可重试
cancelled你点了停止
interrupted服务重启 / 被停，页面上的「继续」就是为它准备的

5. 谁能干什么（权限）

权限分两层：岗位能发起的动作，和能不能碰工作目录里的文件。

岗位默认能做的动作工作目录权限说明
协调者
coordinator		 派发、提问、收尾、否决 不能读写 只负责组织和拍板，不许自己写代码 —— 靠工单往下派
实施者
engineer		 提交、派发、否决 可读可写（限目录内） 真正的劳动力，所有改动都必须落在共享工作目录里
审查者
reviewer		 审查、否决 只读 只看不改；发现越权改动会被审计记下来并标红

那「协调者不能读文件」不会误事吗？

不会，它也不需要：它靠工单里的结论和产出文件清单来判断，而不是自己去翻目录。 这也正是下面第 9 节要讲的「交接规则」。

共享工作目录是整个协作组共用的同一个文件夹。所有智能体拿到的是同一个绝对路径， 「只读」「不许越界」靠提示词约束 + 运行前后的越权审计兜底（实现者改了不该改的目录会被当场发现）。

6. 工单的一生（状态）

状态大白话
open刚开出来，还没人动手
working有人正在干
waiting_children我把它拆成了子工单，等下面的活先干完
review提交了，等审查者看
rework被打回了，正在按要求返工
escalated下级把「我搞不定」上报上来了，等派活的那个人处理
done收尾了（附一句结论）
rejected被否决，这条分支终止
blocked卡住了，在等你拍板 / 或撞上了护栏

整个协作运行本身也有状态：running（跑着）、waiting_user（等你）、 done（完成）、error（出错）、cancelled（你点了停止）、 interrupted（服务中断/被停）。

7. 工单里装了什么

派活时填的（brief）

  • 目标：这件事要达成什么
  • 需求：具体要做哪几件事
  • 验收标准：怎么算干完了（最重要）
  • 约束：不许碰什么、不许加什么
  • 交付物：要交出什么

交活时填的（result）

  • 结论：一句话说清干成了什么
  • 产出文件：改了/生成了哪些文件

这张「交付摘要」是给上游看的唯一凭证：上游汇总、最终汇报，看的都是它。

结论写空 = 等于没交付。过去「收尾（done）不带结论」就是事故源头之一： 上游只看到一张「完成了」的空壳，只能重新派人再干一遍。

8. 成员看到什么：一次输入的解剖

这是整套机制里最反直觉的一条：智能体之间不共享对话。每个岗位每次动手，拿到的都是一份 现场拼出来的工单说明，而不是前面那几个人的聊天记录。把它拆开，就是下面这几层：

① 岗位协作组、岗位名、职责、能力边界 —— 「你是谁、在这个组里干什么」
② 工作路径唯一允许访问的目录 + 权限（无 / 只读 / 可读写） —— 所有岗位拿到同一个绝对路径
③ 输出协议本轮允许的动作、能派给谁、审查者是谁、退回给谁、工单块模板 —— 只能做协议里写的事，越权会被运行时拦下
④ 工单字段标题 / 目标 / 需求 / 验收标准 / 约束 / 交付物 —— 派活时填的那张单子，原样给到
⑤ 上游交付摘要上一手的一句话结论 + 变更文件清单 —— 摘要，不是聊天原文
⑥ 下游交付我派出去的直接子工单：状态、最后经手人、结论、产出 —— 「我派的活交回了什么」
⑦ 本工单历史这一张工单上的最近几轮：谁提交、谁打回、意见是什么 —— 只有这一张工单
⑧ 本轮要求引擎按岗位和当前状态写的一句话：这轮该提交、该审查，还是该汇总 —— 和协议永远一致，不会自相矛盾

收尾汇报那一轮会多一块「全流程结果」：把整次协作的工单压成「标题 · 状态 · 结论 · 产出文件」， 让入口智能体有东西可讲。

刻意不进来的东西

别人的对话原文 —— 一个字的通路都没有（不是靠自觉，是数据里根本没存）
别的工单正文 —— 只拿得到自己这一张；子树的细节逐级向上压缩成结论
别的分支 —— 兄弟工单干到哪了，这边看不见
上一次的内核会话 —— 每一步都是全新会话，不续接、不带记忆
所以「交接」靠的只有四样东西：工单字段、一句话摘要、产出文件路径、本工单历史。 这也是为什么结论写空会要命 —— 那就是下游能拿到的全部信息。 另外还有一层不属于工单：智能体的人格（「你是谁」的设定）配在智能体页，走的是系统提示词， 协作流程只负责往这份人格上叠岗位与工单。

9. 交接规则：谁看得到什么

这是整套机制里最容易被忽略、也最关键的一条：智能体之间不共享记忆。

  • 每个智能体干活时都是全新会话，看不到别人聊过什么；
  • 它只能看到：工单字段 + 一句话摘要 + 文件路径清单；
  • 上游能看到的，是派活时那张工单的内容；
  • 下游能看到的，是上游留下的交付摘要；
  • 子工单干完了，它的结论也会作为「下游交付」出现在上游那一轮的输入里。
  • 干不动了也能往上报：把工单交回「派活给我的那个人」，附上一句「卡在哪、需要什么」； 一级一级报到入口智能体，最后由 CEO 统一来问你。
「下游交付」这一条就是这次修的核心：以前上游只看得见自己几次「我派出去了」的记录， 看不到下游交回了什么，于是把「已经干完」误判成「还没回报」—— 接下来第 13 节会讲这个真实事故。

10. 中断与续接：停了以后从哪接着跑

协作会跑很久，谁都可能锁屏、关页面、撞上服务重启。原则只有一条： 中断的是「这一次推进」，不是整件事。工单和已经产出的东西都留着，恢复后只跑没干完的。

点「停止」当前这一步立即取消（子进程被杀），运行标为已停止；已经收尾的工单、写好的文件和结论全部保留，未完成的那一步可以重试。
锁屏 / 关页面 / 断网不会打断运行：推进跑在后台，页面只是订阅它。重新打开页面、换台设备，都能接着看同一份实时进度，正在跑的步骤不会重来。
服务重启 / 崩溃启动时把残留的「进行中」运行标成已中断，把还挂着「处理中」的步骤一并收尾（否则界面会永远转圈）。工单原状态不动，点「继续」从就绪队列接着跑。
模型输出不合协议不猜、不抛异常：这一步标失败、工单标卡住、运行停下来等你。修好模型或剧本后点「重试」，那张工单重新进队列，再「继续」。
返工太多 / 拆得太深 / 预算用尽撞护栏，同样挂起 + 红字说明原因。调大上限或换条路，再从挂起的地方继续 —— 不会悄悄空转烧钱。
心跳页面每 15 秒收到一行「还在」的注释，只为防止代理把长连接掐掉。它不会打断正在等模型回答的那一步：安静很久之后才出结果，也是正常的。

「继续」到底继续了什么

  • 从就绪队列接着跑：只有还没收尾的工单（待领取 / 返工）会被重新推进，已完成的不会重做；
  • 续的是工单，不是记忆：每一步仍是全新会话，靠工单字段、摘要和产出文件接手；
  • 等你拍板期间不算超时：空闲时限按「距上次进展」算，隔一天回来继续，仍有一个新的推进窗口；
  • 拿不准从哪继续，先在主会话里问入口智能体「现在做到哪了」，它会照着工单快照回答。
如果「继续」之后还是立刻停住，先看红字：多半是同一处没修好（密钥没填、目录权限不对、输出一直不合协议）。 同一个原因会一直停在同一张工单上，不会自己好。

11. 所有消息先给 CEO：要不要推进由它判断

入口智能体（CEO / 小组长）在大多数时候是空闲的：真正动手的是下游岗位。 所以你随时可以在输入框里继续和它说话，不需要等整条流程结束 —— 闲聊、问进度、 补要求、加新活，全都从同一个输入框发出，不需要选模式。

要不要把任务推进起来，由 CEO 判断。它觉得只是聊聊，就正常回你； 它觉得这需要真正动手（新任务、继续推进、答复系统的提问），就会在回复后面给你一张 「推进任务」决策卡：上面有它的理由和建议的指令，点一下选项，指令才进入工单通道 开始跑。不想推进就点卡片上的「×」，把它当普通聊天。

有等待你决定的问题时，卡片上的指令会直接作为对那个问题的答复发出， 不用再组织语言。
如果某张工单卡住了（例如报「只有入口节点能向用户提问」），页面会给出错误卡和一键「重试」， 并说明卡在哪里。点重试后会从那张工单重新跑；想先了解情况，直接问 CEO 即可。
你可以问 / 说会发生什么
「现在做到哪了？」CEO 看系统给的工单快照，告诉你谁在做、哪张工单在什么状态、最近结论和产出文件
「再加一条要求：……」「验收改成……」CEO 正常回复你，并把新要求同步进还没收尾的工单；下一轮步骤开始按新要求做
「加一个导出按钮」「继续做下一阶段」CEO 判断需要动手，给你一张推进任务决策卡（理由 + 建议指令）；点选后才开始跑
「这个方案是什么意思？」「辛苦了，聊两句」正常聊天、解释方案，不会打断主流程，也不会改变工单状态
它不是“共享记忆”。聊天原文只给入口智能体本人看；其他岗位仍然只拿到工单字段。 CEO 也不能在聊天里直接改工单状态、派活或建子工单 —— 它只能把你明确补充的要求写进工单、 或给出推进建议等你确认，真正的流转仍由原来的规则执行。
正在执行的那一步已经拿到指令了，所以新要求不会中途塞进去；它会从下一步开始生效。 如果你要的是“立刻停掉重来”，先点「停止」，再在对话里说明。

12. 防死循环的护栏

协作会花钱花时间，所以系统不会「让它一直转」。撞上任一条护栏，都会挂起等人处理， 并且明说原因，绝不悄悄空转。

护栏作用
返工轮次上限同一张工单被打回太多次就停，喊你来看
拆解层数上限（5 层）防「子工单再拆子工单」无穷套娃
同名子工单上限（2 张）防「换个说法重复派同一件事」，近似的标题也算
上抛件不许再往下派上报上来的阻塞，只能「解决」或「继续往上」；想换个说法又派回去，系统会直接拦下
运行预算步数 / 工单数 / token 上限；超了就挂起
空闲超时按「多久没有新进展」算，不会因为你隔天回来继续就失效
单次推进上限一条消息内最多推进 200 步，杜绝无限自转

13. 这次修的是什么（真实事故复盘）

一次「你好，你看看现在的路径有哪些文件」的协作，跑了 23 步、11 张工单， 直到你手动点「停止」才停。下面是它和修复后的对比。

❌ 修复前：转圈

  1. CEO 拆一张子工单给 CTO
  2. CTO 转给码农，码农干完点「完成」
  3. 系统把父工单退回给 CEO，但不带回码农的结论
  4. CEO 看不到结果，以为没干，再拆一张几乎一样的工单
  5. ……回到第 1 步，反复 8 轮

✅ 修复后：回流

  1. 码农收尾时必须写下结论，结论存进工单
  2. 父工单退回时，子工单的结论一起带回去
  3. 上游这一轮的输入里出现「下游交付：…结论…产出文件…」
  4. 系统同时提醒：「能收尾就收尾，别为了再确认一遍重复派发」
  5. 上游判断已完成 → 收尾 → 入口智能体向你汇报

另外，护栏也补强了一条：以前只有标题一字不差才算「重名」， 模型只要在标题尾巴上加几个字（「列出文件清单」→「列出文件清单并回报」）就绕过去了； 现在近似的标题同样会被拦住。

一句话总结这次修复：把「信息断头」接上 —— 让上游看得见下游到底交回了什么， 并且明确告诉它「活已经干完了，可以收尾了」。

第二次修复：卡住了，要能往上走

一次「帮我写一个建筑工程的业务记账系统」的协作里：UI 要做实测，但当前权限模式下智能体 不能执行命令（那是另一件事，改权限就好），它只能把这句话写进「完成」的结论里。

❌ 修复前：往下一压，白转一轮

  1. UI 报「跑不了」，但它的动作里只有「完成」一个，说不出「我卡住了」
  2. CTO 收到后也没有「上报」这个动作，能派的只有码农和 UI（全是往下）
  3. 于是它把同一件事改写成「静态核对，全程不执行任何命令」，又派给码农
  4. 静态核对永远跑不出运行证据，白烧一轮，你什么都没收到

✅ 修复后：逐级上报，CEO 来问你

  1. UI 用 escalate 上报，写清「卡在哪、需要什么」
  2. 工单交回派它活的那个人（CTO）；CTO 解决不了，继续往上
  3. 到了入口智能体，它把问题转成一张可点选项卡交给你
  4. 你回答后，工单交回原来那张接着跑，不用从头再来
一句话总结这次修复：给「我搞不定」修了一条正式的路 —— 上报只朝上走、不许原地往下压；到顶了就变成问你的一张卡片。

14. 卡住了，你能做什么

界面上的东西它的意思 / 你该做什么
状态变成「等你决定」 有人 ask_user 提问了，输入框上方会弹出可点选项，点一下或者自己补充说明
弹出红色提示 多半是撞了护栏（返工太多 / 拆太深 / 标题重复 / 预算用尽），提示里写了具体原因和怎么改
「📋 工单看板」 三栏看板：左边是工单列表（标题 / 状态 / 现在谁在处理），中间是这张工单的流转时间线 （谁把什么交给了谁，一条一步；彩色徽章标出派发 / 提交 / 审查 / 完成 / 提问 / 上报 / 否决）， 右边是派发时定下的规则（目标 / 要求 / 验收标准 / 约束 / 交付物）。 token、耗时这类技术数字都压在小字里；只读节点却动了工作目录会整条翻红并列出被改的文件。 手机上也能看：协作运行页状态行上的「📋 工单看板」点进去，上面选工单、下面切「流转 / 工单规则」
「🧭 协作进度」 整次协作画成一张分层流程图：第一行是领导者一个人，第二行是她直接派活的人， 再往下并排一行是干活的（3 个人干活就是一行 3 个节点）。往下的箭头就是派活方向， 打回 / 返工画成往回走的虚线
节点 每个岗位是一个节点，只放头像 + 昵称；头像右上角的小徽标就是状态： 绿▶=执行中、黄?=在等你决定、红!=出问题、灰…=还没轮到、 绿✓=已完成。还没轮到的岗位整张卡片会淡一点
进度页怎么看细节 拖动平移、滚轮（手机上双指捏合）缩放、右下角 ⤢ 一键复位； 点节点弹出详情卡：她现在具体在做什么、最近动作、跑了多少步、几张工单在处理， 卡上「查看实时对话 →」能直接翻到该岗位这一轮的实时输出
工单状态显示「已上报」 某个岗位把「我搞不定」交回了派活的人，正在逐级往上报；到 CEO 那里会变成一张问你的卡片，此时你先不用动
输入框一直可用 任务在跑也能给 CEO 发消息：问进度、补要求、解释方案；新要求从下一轮步骤生效
「停止」 真的在空转就停下来。工单和产出都会保留，之后可以「继续」
提醒右上角的「×」 关掉这条提醒。失败那类会记住（刷新也不再冒出来）；等状态真的又变了，它才重新提醒你
提醒自己消失 协作收尾了、这个岗位上一次已经跑通、或者同一件事已经报过好几遍 —— 旧的提醒都会自动退休， 留在上面的只应该是「现在还需要你处理」的那几条
「继续」 挂起（等你拍板 / 出错）修好之后从这里接着跑，不会从头再来
「继续」时报 cannot be used with root/sudo privileges 本机以 root 运行，而岗位勾了 bypassPermissions（跳过全部权限检查）—— Claude Code 在这种组合下会直接拒绝启动。系统会自动补上它要的 IS_SANDBOX=1； 若还在报，先重启服务，再检查是不是自己在智能体的环境变量里把 IS_SANDBOX 设成了别的值
只有入口智能体的那条主会话是给你看的；其他智能体的对话不打扰你， 但它们随时能在「工单看板 / 协作进度」里查到 —— 看得少，但看得清。
