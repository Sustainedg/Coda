# 上下文窗口与自动压缩（功能文档）

> 面向使用者与维护者。实现细节与口径以本文为准；逐内核对接与内部实现见
> `docs/说明/context-usage.md`。
>
> - 后端核心：`backend/app/runtime/context.py`（**唯一一份口径**）
> - 事件协议：`backend/app/agents/events.py`
> - 运行层：`backend/app/runtime/service.py`
> - 前端：`frontend/src/components/ContextMeter.tsx`、`frontend/src/lib/contextUsage.ts`

---

## 1. 这个功能解决什么问题

对话越长，模型能"看到"的上下文越有限：超限时要么被内核直接拒绝（报错），要么用户毫无察觉地
被截断。这个功能让用户**看得见**上下文用了多少、还剩多少，并在逼近上限时**自动**把较早的
对话折叠成摘要，保证长对话能继续跑下去。

它同时解决两个问题：

1. **计量**：真实的上下文占用是多少？——尽量用内核上报的真实数字，没有才按内容估算。
2. **压缩**：什么时候该压、压什么、压完怎么算？——平台有一套确定性压缩，内核也各有一套原生
   压缩，两套并存、互不替代。

**贯穿全模块的一条铁律**：展示、阈值判断、压缩决策**必须共用同一份口径**（都在
`runtime/context.py`）。否则会出现"面板说没超，压缩却触发了"这种自相矛盾。

## 2. 用户视角

### 2.1 输入框上方的「上下文」按钮

聊天输入框上方常驻一枚按钮，一眼看到：

```
上下文 12.4k/200k   6%
```

- 左边是**已用**，右边是**上限**，后面是百分比。
- 进度条颜色随风险变化：正常 → 接近阈值（黄）→ 已超限（红）。
- 压缩发生后按钮上多一枚徽标：`已压缩` / `压缩中` / `压缩失败`。

### 2.2 详情面板

点开按钮，面板向上展开（与输入区齿轮同款观感），里面是：

| 字段 | 含义 |
| --- | --- |
| 当前已用 | 真实的上下文占用（快照优先，否则估算） |
| 可配置上限 | 当前**生效**的上限（自动模式下 = 内核窗口） |
| 内核窗口 | 内核自己上报的模型真实窗口；没报过显示"内核未上报" |
| 触发阈值 | 达到多少就触发自动压缩（绝对值 + 百分比） |
| 压缩策略 | 保留多少最近消息、怎么折叠 |

下面是可编辑区：

- **上限来源**：`跟随内核` / `手动设置` 两个按钮（详见 §5）
- **上限（tokens）**：手动模式下可填；跟随内核时只读
- **触发阈值（%）**：默认 80%

面板贴着输入区，**打开面板、保存配置都不会禁用输入框**——用户随时可以继续打字。
运行中每 2.5 秒轻量刷新一次（只发一个请求：用量），让数字跟着本轮走。

### 2.3 界面上的两个"诚实声明"

平台不会假装知道它不知道的东西：

- 用量**不是**内核真实快照时，面板底部明确写"按字符近似估算：中日韩文字约 1 字 = 1 token…"，
  `measured` 字段为 `false`。
- 该内核**没有**原生压缩能力时，本文 §6.1 逐内核写明"平台压缩就是唯一压缩"，不会让人误以为
  还有一层内核压缩在兜底。

## 3. 计量口径（唯一一份）

取数分两档，展示、阈值判断、压缩决策**全部**走 `runtime/context.estimate_conversation()`。

### 3.1 第一档：内核上报的真实快照（优先）

会话型内核自己维护上下文，平台看不到它内部的历史。适配器在**每次模型请求**后上报一条
`context.usage` 事件，运行层把它记到 `messages.context_tokens`：

| 内核 | 取数位置 |
| --- | --- |
| Claude Code / CodeBuddy | `message_delta.usage`（主）、`message_start.message.usage`、完整 `assistant` 消息的 `message.usage` |
| DeepSeek Harness / OpenAI Harness | 每一步的 `prompt_tokens` |
| Codex app-server | `thread/tokenUsage/updated` 的 `last.inputTokens` |

口径细节：

- **Anthropic 风格**（`input_tokens` 与 `cache_read_input_tokens` 分离）→ **相加**；
- **OpenAI 风格**（`prompt_tokens` 已含 `cached_tokens`）→ **不能重复加**。
- `result` 里的用量是**整轮累计**，**不能**当窗口占用。

> #### ⚠️ `message_delta` 才是窗口占用真正的来源
>
> Claude Code 2.1.327 实测：`message_start` 的 usage **常常是全 0**，真实数字推迟到
> `message_delta` 才给。适配器若按旧版行为跳过 `message_delta`（"它只有 output_tokens"），
> 内核就**永远报不出窗口快照**——面板会一直显示「按内容估算」，而内核其实早就把真实
> 数字给出来了。同一轮工具循环的实测：
>
> | 帧 | input_tokens | cache_read | 含义 |
> | --- | --- | --- | --- |
> | `message_start` | 0 | 0 | 全 0，不可用 |
> | `message_delta` | 75 | 14848 | 本次请求的窗口占用 ✅ |
> | `message_start` | 0 | 0 | 全 0，不可用 |
> | `message_delta` | 232 | 14848 | 第二次请求（多了工具结果）✅ |
> | `result` | 307 | 29696 | **整轮累计**，不能当窗口占用 |
>
> 老内核若 `message_delta` 真的只有 `output_tokens`，`context_tokens()` 会算出 0，不会误报。

下一次估算以**最近一次请求的输入 token** 为基准，再加上此后新增的正文。

> **记录网关（`CODA_RECORDING_GATEWAY`，默认关闭）开启时，运行中直接读一手账本**：
> `usage_records` 里当前 run 最新一行的 `context_tokens`（代理从上游 `usage` 归一化）比内核
> 二次上报更可信，且请求终态就已落账——消息还没落库时面板也能看到最新数字。**原生 /
> harness 的 `context.usage` 事件也实时入账**（每个 run 一行、运行中更新，收尾补计费），
> 因此官方直连内核在运行中同样能从账本读到真实窗口，不必等收尾。运行结束后仍以
> `messages.context_tokens` 快照为主（账本行用于校准），避免「最新请求 + 其后消息」重复
> 计算。详见 `docs/功能文档/usage-gateway.md`。

### 3.2 第二档：按内容估算（没有快照时的兜底）

| 内容 | 估算规则 |
| --- | --- |
| 中日韩文字（含全角标点、假名、谚文） | 1 字 ≈ 1 token |
| 其余字符 | 4 字符 ≈ 1 token |
| 每条消息 | 额外 4 tokens（角色 / 分隔开销） |
| 工具调用 | 工具名 + 入参 JSON |
| 工具结果 | 输出全文 |
| 推理内容（thinking） | 全文 |

估算范围按内核能力区分，保证"算的就是真正会发出去的"：

- **会话型内核且会话还在**：内核转录里装着工具调用与工具结果 → 按**全部有效消息 + 工具片段**估算；
- **非会话型内核**（或会话已被压缩 / 重置）：平台只回放最近 **24 条 / 40000 字符**的**最终回复**
  （与 `runtime.service` 实际发送的历史同一份规则），工具片段不计。

注意：`text` 片段与 `content` 是同一份内容，只计一次；正文为空但带 `parts` 的消息（只调工具、
还没产出文字的回合）不会被丢掉——它同样占内核上下文。

> 这是**近似估算**（快照档除外），不是计费口径。各内核上报的 `usage` 是整轮累计，
> 用来做用量与计费统计，**不能**当"当前窗口占用"。

### 3.3 快照什么时候失效

以下任一情况，快照作废，估算回落到 §3.2：

| 失效条件 | 说明 |
| --- | --- |
| 会话被压缩 / 重置 | `session_id` 被清空 |
| 快照来自 @ 召唤轮 | 召唤轮不写回主场会话记忆，它的数不能拿来当家主的 |
| 快照早于最近一次**平台压缩** | 平台压缩清 session_id，旧快照随之失效 |
| 快照早于最近一次**内核原生压缩** | 内核压缩不动会话，但压缩前的窗口占用已不代表当前上下文 |

> #### ⚠️ 关键实现细节：比的是「快照采集时刻」，不是「消息创建时刻」
>
> 本轮消息在**轮次开始时**就建好了（`created_at`），而快照产生于**本轮中间**某次 API 调用
> （`context_snapshot_at`）。内核原生压缩后上报的 `post_tokens` 正是"消息早、快照晚"的情况。
>
> 如果拿 `created_at` 去比压缩时刻，压缩后的新快照会被**自己的失效线误杀**：估算回落到
> 按内容估算，而内容里还包含内核**已经折叠掉**的历史 → 用量虚高数倍（实测 6 倍）→
> 反过来触发一次**多余的平台压缩** → 平台压缩清 `session_id` → 内核好不容易保住的会话连续性被打断。
>
> 所以 `messages.context_snapshot_at` 单独记录快照的采集时刻，失效判定比它。

## 4. 平台自动压缩

### 4.1 触发时机

`prepare_run`（发送前）与 `regenerate_last`（重新生成）都会先估一次"系统提示 + 历史 + 本轮提示"，
达到阈值就压缩。**失败不打断本轮对话**，本轮沿用原始历史。

### 4.2 压缩策略（确定性裁剪 + 摘要）

不调模型、不阻塞用户输入：

1. **保留系统提示**（不动内核的人设）；
2. **保留最近若干轮**：从最新一条往前装，装到"上限的一半"为止，最多 **8 条**、最少 **2 条**；
3. **更早的历史折叠成摘要**：一行一条（用户/智能体 + 首 80 字），摘要最多占上限的 **1/5**；
4. **原始消息一条不删**，仍完整保存在 `messages` 表里——对话记录、导出都不受影响；
5. **压缩后清掉内核侧 `session_id`**：会话型内核无法在自己的面板里裁剪上下文，这一轮改用
   "摘要 + 最近若干轮"注入；下一轮内核会建立新会话。

### 4.3 失败兜底

例如"最近两条本身就超过目标"，则**不改任何已存上下文**，本轮沿用原始历史，并通过运行日志 +
按钮徽标给出"压缩失败，已保留原上下文"的提示。同一对话有占位（`begin_compaction`），不会重复触发。

### 4.4 状态展示

最近一次压缩的状态（进行中 / 成功 / 失败）通过 `GET /api/conversations/{id}/context` 返回，
按钮上显示徽标、面板里显示详情。

## 5. 上限对齐：跟随内核还是手动设定

平台默认上限 **128k / 80%**，但那只是"平台不知道内核真实窗口"时的保守值。Claude Code 实际
可能是 200k 或 1M，Codex 会直接告诉你 `modelContextWindow`。

因此上限有两种模式：

| 模式 | 行为 | 适合 |
| --- | --- | --- |
| **跟随内核**（`auto`，默认） | 上限 = 内核上报的真实窗口；内核没报过时退回用户配置值（默认 128k） | 想让内核自己管窗口，平台别抢戏 |
| **手动设置**（`manual`） | 上限 = 用户填的值，**永远**以用户为准 | 想在远小于内核窗口时就主动压缩 |

**内核窗口从哪来**（新增事件 `context.window`）：

| 内核 | 来源 | 可靠度 |
| --- | --- | --- |
| Codex app-server | `thread/tokenUsage/updated` 的 `tokenUsage.modelContextWindow` | ✅ 官方 schema 明确，字段稳定 |
| Claude Code | 顶层 `autocompact_state` 帧的 `value.effective_window` | ⚠️ 解析器已实现，但 **2.1.327 的 `-p` print 模式实测不下发该帧**（只出现在 SDK / 云端会话路径），所以实际多半走兜底值 |
| CodeBuddy 等 | 暂不上报（协议里没有） | — |

> 为什么保留 Claude Code 的解析器：帧格式来自内核自身的 schema（`effective_window` 是
> "resolveAutoCompactWindow 的结果，已按模型窗口夹取"），一旦某个版本 / 模式开始下发，
> 平台无需改动即可自动接上；接不上也只是退回兜底值，不影响任何行为。

> Codex 的窗口为什么可信：`modelContextWindow` 写在**官方 JSON Schema** 里
> （`codex app-server generate-json-schema` 可直接导出），字段名与类型都是契约的一部分。

**兼容性**：升级前保存过配置的用户，那行数据没有模式字段 → 读作 `manual`，行为与从前一致，
不会被自动改掉上限。

> 自动对齐**永远不会覆盖人的选择**：只要用户显式设过上限，就以用户为准。

## 6. 与内核原生压缩的协同

平台压缩与内核压缩是**两套独立机制**，可以并存：

| | 平台压缩 | 内核原生压缩 |
| --- | --- | --- |
| 触发 | 平台上限达到阈值 | 内核自己的窗口 / 阈值 |
| 动作 | 折叠成摘要 + **清 `session_id` 重开会话** | 在会话内折叠，**会话连续** |
| 影响 | 历史改为平台注入 | 内核自己的转录 |

协同的三个对接点：

1. **事件接收**：适配器解析内核的压缩信号，上报 `context.compacted`（字段白名单透传），
   运行层发中文提醒，并记下 `conversations.context_kernel_compacted_at`。
2. **快照失效**：内核压缩不动会话，所以要用时间戳让压缩前的快照作废（§3.3）。
   若内核上报了 `post_tokens`（压缩后的窗口占用），它直接成为最新快照。
3. **参数透传**：智能体配置里的 `autocompact`（高级选项）透传 `--autocompact`，留空走内核默认。
4. **配置生成**：平台把生效的上限 / 阈值翻译成内核自己的压缩配置——Claude Code 下发
   `CLAUDE_CODE_AUTO_COMPACT_WINDOW` / `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`（百分比按 100K–1M
   夹取后的窗口算），Codex 下发 `-c model_context_window` / `-c model_auto_compact_token_limit`。
   这样「平台压缩」和「内核原生压缩」共用同一阈值；用户显式设了 `--autocompact` 时不覆盖。

### 6.1 各内核对接现状

各内核 wire 协议不同，**必须逐内核对接**。下表基于**实测 CLI 二进制与官方 schema**：

| 内核 | 窗口快照 | 原生压缩事件 | `autocompact` 透传 |
| --- | --- | --- | --- |
| Claude Code | ✅ | ✅ `system/compact_boundary` + `compact_metadata` | ✅ |
| CodeBuddy | ✅ 同构 | ✅ `system/compact_boundary`（`-p` 会话手动 `/compact` 时发出，只带 `trigger` / `pre_tokens`） | ✅ |
| Codex app-server | ✅ | ✅ 新协议 `item/completed` 的 `contextCompaction`；老版本 `thread/compacted`（官方标 Deprecated，两个都认） | ✖（由内核自身配置控制） |
| DeepSeek / OpenAI Harness | ✅ 每步 `prompt_tokens` | 无（平台压缩就是唯一压缩） | — |
| Antigravity CLI / Custom CLI | ✖ 只有终态累计用量 | ✖ | — |
| Doubao CLI | ✖ 协议不上报 token 用量 | ✖ | — |
| Hermes | ✖ `stream-json` 只给整轮累计 token | ✖ 不暴露内部 context engine 的压缩 | — |

> **实测补充（CodeBuddy）**：`-p` 模式下除 `system/init` / `assistant` / `result` 外，还会下发
> `system/usage_update` 帧，用量放在 `_meta["codebuddy.ai/turnUsage"].total.usage` 里，
> 且标注了 `scope: "turn"` / `kind: "snapshot"`。因为它是**整轮累计**口径，直接当成
> 「单次请求的窗口占用」会把多步工具循环的输入累加进去（窗口被高估），所以平台**不**拿它
> 做窗口快照；窗口占用取 `message_delta`（CodeBuddy 与 Claude Code 同源，见上）。


> **端到端实测（真实内核 + 真实旧库）**：从工作树起服务、挂 `backend/data/coda.db` 的副本、
> 用真实 claude-code 智能体跑一轮对话——修复前 SSE 里**没有** `context.usage`，落库
> `context_tokens` 为 NULL，面板显示「按内容估算」；修复后 `context.usage tokens=13919`、
> 落库 `context_tokens=13919` + `context_snapshot_at` 有值、面板 `measured=true`。
> 也就是说：**在接上 `message_delta` 之前，内核明明把真实数字报出来了，平台却一直没接住**，
> 面板长期显示的是估算值。
> **这些结论是怎么来的（别照抄，要自己复核）**：
>
> - **实机跑出来的**：CodeBuddy 的 `-p` 帧序列（`system/init` / `assistant` / `result` /
>   `system/usage_update`）、`--autocompact 400k` 被接受；Claude Code 的 `-p` 帧序列
>   （`system/init` / `assistant` / `result`，**没有** `autocompact_state`）；
> - **从二进制 / 官方 schema 读出来的**：Claude Code 的 `compact_metadata` 字段名与类型
>   （`strings` 挖二进制里的 zod schema）、Codex 的 `ContextCompactedNotification` /
>   `ContextCompactionThreadItem` / `modelContextWindow`（`codex app-server generate-json-schema`
>   导出官方 JSON Schema）、Hermes 的 stream-json 事件集（读它的 `stream_json.py` 源码）；
> - **尚未实机触发过的**：Claude Code 与 CodeBuddy 的 `compact_boundary`（要真的把上下文
>   压一次才会发，代价高）。协议字段来自内核自身的 schema，解析逻辑有单测覆盖，但
>   「真实压缩时确实会按这个形状发」尚未端到端验证过。

> **没有快照的内核不会"假装有数"**：`measured = false`，界面明确显示"按内容估算"，
> 阈值判断与压缩决策照常工作。

## 7. 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/system/context` | 读当前用户的上下文配置（上限、阈值、上限模式） |
| `PUT` | `/api/system/context` | 保存配置；非法输入 422 且**不落盘** |
| `GET` | `/api/conversations/{id}/context` | 一条对话的用量 + 阈值 + 压缩状态（按钮的数据源） |

`PUT /api/system/context` 请求体：

```jsonc
{
  "limit_tokens": 128000,       // 手动模式下的上限（自动模式是兜底值）
  "threshold_ratio": 0.8,       // 触发阈值（占上限的比例）
  "limit_mode": "auto",         // auto（跟随内核）/ manual（手动设置）
  "conversation_id": "可选"      // 带上就校验「上限不得低于该对话当前已用量」
}
```

校验规则（前后端各一道，**服务端为准**）：

- 上限必须是正整数、≥ 1000；
- 阈值必须满足 `0 < 阈值 ≤ 100%`；
- 上限模式只能是 `auto` / `manual`；
- 带了 `conversation_id` 时：上限不得低于该对话当前已用量（自动模式按**实际生效**的上限
  校验，即内核窗口；手动模式按用户填的值）。前端在自动模式下不校验上限那一栏——
  那一栏是只读的，不能因为显示成「已超限的样子」就把人卡住不让改阈值。

`GET /api/conversations/{id}/context` 响应（节选）：

```jsonc
{
  "used_tokens": 12400,
  "limit_tokens": 200000,          // 实际生效的上限
  "configured_limit_tokens": 128000,
  "kernel_window_tokens": 200000,  // 内核上报的真实窗口（没报过 = null）
  "limit_mode": "auto",
  "limit_source": "kernel",        // kernel / user / default
  "threshold_tokens": 160000,
  "threshold_ratio": 0.8,
  "percent": 6.2,
  "measured": true,                // 是否以内核真实快照为准
  "compacted_count": 12,
  "compaction": { "status": "ok", "before_tokens": 180000, "after_tokens": 42000, "dropped": 12 }
}
```

## 8. 数据模型

```
conversations
  context_summary              平台压缩折叠出的摘要（原文仍在 messages 表里）
  context_compacted_count      已折叠进摘要的消息条数（偏移量，历史一条不删）
  context_compacted_at         最近一次平台压缩的时刻
  context_kernel_compacted_at  最近一次内核原生压缩的时刻（让压缩前的快照失效）
  context_kernel_window_tokens 内核上报的真实窗口（上限「自动」模式跟随它）

messages
  context_tokens               本轮最后一次模型请求的输入 token（窗口快照）
  context_snapshot_at          该快照的**采集时刻**（≠ 消息创建时刻，§3.3）
```

配置存在平台设置表（`platform_settings`），键 `context_settings:<owner_id>`，值形如：

```jsonc
{ "limit_tokens": 128000, "threshold_ratio": 0.8, "limit_mode": "auto" }
```

## 9. 事件协议

| 事件 | 载荷 | 用途 |
| --- | --- | --- |
| `context.usage` | `payload.tokens` | 单次请求的输入 token（窗口占用） |
| `context.window` | `payload.tokens` | 内核上报的真实上下文窗口大小 |
| `context.compacted` | `payload.trigger/pre_tokens/post_tokens/messages_summarized…` | 内核原生压缩通知 |

## 10. 给新内核接入的步骤

以新增一个内核 `foo-cli` 为例：

1. **找真实窗口**：在内核的 wire 协议里找**单次请求的输入 token**（不是整轮累计用量）。
   找到后发一条 `context.usage` 事件。
2. **找压缩信号**：内核压缩完成时有没有事件 / 通知 / 条目？找到后发一条 `context.compacted`
   事件（字段按白名单透传）。
3. **找真实窗口大小**（可选）：内核有没有自报模型窗口（Claude Code 的 `effective_window`、
   Codex 的 `modelContextWindow`）？有就发一条 `context.window` 事件。
4. **参数透传**（可选）：内核支持 `--autocompact` 之类的开关，就在配置里加一个高级字段透传。

要点：

- 适配器只能依赖 `agents/*` 与标准库，**不得反向依赖** `runtime` / `models` / `api`（有架构测试守着）；
- 新增事件必须**四处同步**：`agents/events.py`、`runtime/service.consume_run`、前端
  `applyEvent` + `types.ts`、`docs/架构/architecture.md` 的事件表（`tests/test_architecture.py` 会查）；
- 事件载荷里不要塞原始遥测字段，用白名单，避免 payload 无限膨胀。

## 11. 排错

| 现象 | 原因与处理 |
| --- | --- |
| 面板显示「按内容估算」 | 该内核没上报窗口快照（见 §6.1），或快照刚被压缩作废（等下一轮即可校准）。**若内核明明报了数却一直显示估算**：多半是适配器没接住内核真正的取数位置（Claude Code 2.1.327 是 `message_delta`，不是 `message_start`），抓一次真实 `-p` 帧流核对 |
| "内核未上报" | 该内核协议里没有模型窗口；可以手动设定上限 |
| 用量突然掉一大截 | 内核原生压缩了：旧消息已折叠，窗口占用随之下降 |
| 用量突然涨一大截 | 刚发生内核压缩、平台还没拿到新快照；下一轮会自动校准 |
| 压缩失败 | 面板会给出原因；常见是"最近两条本身就超过目标"，此时保留原上下文继续 |
| 面板数字与内核对不上 | 先确认是不是手动模式（手动模式下平台口径 ≠ 内核口径） |
