# 任务进度卡（功能文档）

> 面向使用者与维护者。本文描述任务进度卡的现状：用户看到什么、模型怎么上报、服务端
> 怎么合并、卡片存在哪里、哪些内核走哪条通道。实现细节以代码为准；本文与代码冲突时，
> 先改代码或先改文档，别让两边长期各说各话。
>
> 核心文件：
>
> - 后端：`backend/app/runtime/task_cards.py`（解析 / 合并 / 落库）、
>   `backend/app/runtime/task_card_mcp.py`（每轮绑定与令牌）、
>   `backend/app/api/task_cards_internal.py`（内部写入口）
> - 内置 MCP：`scripts/mcp/task_card_mcp_server.py`、`backend/app/builtin_mcp.py`
> - 前端：`frontend/src/components/TaskProgressCard.tsx`、
>   `frontend/src/lib/taskCardFence.ts`、`frontend/src/lib/taskCardCollapse.ts`

## 1. 这个功能解决什么问题

多步骤任务里，用户最想知道的是「现在做到哪了、还剩几步」。任务进度卡把这件事做成
对话级的状态栏：

- 模型开始一项多步骤工作时，给出计划（2～20 项）；
- 之后每完成一步，只上报变化项；
- 卡片常驻输入框上方，显示标题、完成数 / 总数、进度条与每一项的三态；
- 卡片只读，不提供勾选、编辑、删除入口——进度由模型上报，用户不替模型改状态。

一句话：**卡片是「这条对话当前做到哪了」的展示面，不是消息的一部分，也不是待办清单编辑器。**

## 2. 用户看到什么

### 2.1 位置与形态

桌面端与移动端都把卡片放在 `Composer` 的 `header` 槽，也就是输入框上方，
不插进消息流。这样历史消息滚走时，进度仍然看得见。

```
┌─────────────────────────────────────────────────────────┐
│ 📋 任务标题 · 进度 3/7            [进度条]      [收起/展开] │
├─────────────────────────────────────────────────────────┤
│ ✓ 步骤一（已完成，划线）                                   │
│ ◐ 步骤二（进行中）                                         │
│ ○ 步骤三（待办）                                           │
└─────────────────────────────────────────────────────────┘
```

- 标题为空时显示「任务进度」。
- 进度显示 `已完成数 / 总数`，同时显示进行中的项数。
- 默认收起；点标题栏展开，Enter / 空格同样可切换，带 `aria-expanded`。
- 折叠偏好只存本机：`localStorage` 键 `coda.taskcard.collapsed`，按卡片 id 记，
  最多保留 50 条；坏数据、隐私模式、写入失败一律降级为「收起」，不影响对话。

### 2.2 什么时候出现

卡片在一轮运行**成功结束**、协议被解析并落库之后出现；流式过程中不渲染半成品，
避免闪出一张空卡。页面刷新、切换对话、重启后端后，通过
`GET /api/conversations/{id}` 返回的 `task_card` 字段恢复。前端 3 秒轮询只在
`card.id` / `version` 变化时更新卡片，不会整页闪烁。

### 2.3 明确不提供的能力

- 没有 `<input type="checkbox">`、没有可点击的任务项、没有编辑 / 删除 / 新增按钮。
- 不做多卡片、历史版本、手动改状态。
- 卡片不写回旧消息，消息仍是不可变的历史原文。

## 3. 模型怎么上报

平台同时支持两条输入通道，最终都落到同一张 `task_cards` 表、同一套合并规则。

### 3.1 通道一：正文围栏

所有内核都能用。模型在正文末尾输出一个围栏块：

````text
```task_card
{"action":"create","title":"一句话任务名","items":[
  {"id":"t1","text":"步骤一","status":"pending"},
  {"id":"t2","text":"步骤二","status":"pending"}
]}
```
````

后续轮次只报变化项：

```json
{"action":"update","items":[{"id":"t1","status":"completed"}]}
```

服务端在运行收尾时解析、剥离、合并、落库。解析容忍三类写法：

- 标准 `task_card` 围栏；
- `json` 围栏；
- 正文收尾处的裸 JSON。

非标准块必须「长得像任务卡」（有 `action`，或 `items` 里是 `id/text/done` 字段），
回复中段举例用的 JSON 代码块不会被误吃。实时流里围栏块可能短暂出现，
前端 `stripTaskCardFence()` 在渲染前剥掉；未闭合的块从起始标记一直剥到文本末尾。

### 3.2 通道二：MCP 工具

声明了 `Capabilities.mcp = True` 的内核可以走内置 MCP server：

| 内核 | 通道 |
| --- | --- |
| Claude Code、Codex、CodeBuddy、Hermes、DeepSeek Harness | 优先 MCP 工具 |
| 其余内核 | 正文围栏 |

工具名 `update_task_card`，server 标识 `coda-task-card`。每轮运行开始时：

1. `prepare_run` 生成一次性 `context_id`；
2. 把 MCP 版协议说明拼进本轮 `ctx.prompt`（**不碰 system prompt**，避免破坏会话缓存）；
3. `prepare_mcp_home` 把内部 server 追加进运行配置；
4. 在对话的内核隔离目录写入凭据：
   `task-card/context-<sha256(context_id)[:16]>/auth.json`（目录 0700、文件 0600）；
5. 运行注册后补齐 binding，轮末 `finish()` 失效令牌并删除凭据目录。

工具参数只允许 `context_id / action / title / items`。`conversation_id`、`run_id`、
`version` 这类字段由服务端决定，模型传了也直接 422。这样模型无法通过编造参数改别的对话。

### 3.3 三态协议

任务项状态只有三种：

| 状态 | 含义 | 前端标记 |
| --- | --- | --- |
| `pending` | 待办 | ○ |
| `in_progress` | 进行中 | ◐ |
| `completed` | 已完成（终态） | ✓ |

规则：

- `completed` 是终态，进入后写 `done_at`，之后改回 `pending` / `in_progress` 一律忽略；
- `pending ↔ in_progress` 允许来回切换；
- 旧协议 `done:true` 等价于 `completed`；
- 旧协议 `done:false` 是 no-op，不能把已完成项改回去；
- 旧卡片行没有 `status` 时按 `done` 推导，不改库；
- 存储里 `done` 是派生布尔，`done = (status == "completed")`。

### 3.4 建卡闸门

不是每一轮都注入协议。服务端同时看两件事：

- 对话里已经有一张卡；或本轮用户消息「像多步任务」（`looks_like_task_request`）；
- 内核是否声明 MCP 能力。

无卡 + 不像多步任务 → 不注入、不建卡。这样闲聊不会被塞一张空进度卡。

## 4. 通道优先级与内核任务桥接

### 4.1 优先级

一轮运行里可能同时出现三条来源：

| 优先级 | 来源 | 说明 |
| --- | --- | --- |
| 1 | MCP | 本轮有成功的 `update_task_card` 调用，围栏与内核快照都忽略 |
| 2 | 围栏 | 没有 MCP 调用时解析正文块 |
| 3 | 内核快照 | 前两者都没有 / 围栏写坏时的兜底 |

无论哪条通道，正文与 parts 里的围栏块都**无条件剥离**，防止协议 JSON 泄漏到气泡或 IM。

### 4.2 内核任务工具桥接

有些内核自带任务工具（例如 CodeBuddy 的 `TaskCreate` / `TaskUpdate` / `TaskList`）。
平台不直接复用内核任务列表，而是在**适配器**里把内核事件归一成平台卡片块：

```
内核 TaskCreate / TaskUpdate / TaskList
        │ 适配器归一
        ▼
AgentRun.task_card_block
        │ 运行层复制
        ▼
ActiveRun.task_card_block
        │ consume_run finally，仅当前两条通道都没有产出时
        ▼
apply_block(source="kernel")
```

归一规则：

- `TaskCreate` 成功 → 新增 `tN`，文本取 subject，状态 `pending`；
- `TaskCreate` 失败 / 认不出任务号 → 忽略，不补占位项；
- `TaskUpdate` → 按任务号改状态，`deleted` 从快照移除；
- `TaskList` → 整卡快照替换，未出现的项视为删除；
- 快照不足 2 项 → 不产出块（平台建卡要求 2～20 项）；
- 标题取第一个任务文本。

这是**有损兜底**：内核任务列表属于内核 session，平台卡片属于 conversation，两者生命周期
不同；不做双向同步，也不直接读内核会话文件。新内核要在自己的适配器里做同样的归一，
设置 `AgentRun.task_card_block` 即可，不需要改运行层的优先级逻辑。

## 5. 存储与合并

### 5.1 数据表

`task_cards`（一个对话一张卡）：

| 列 | 用途 |
| --- | --- |
| `id` | 卡片标识 |
| `conversation_id` | 对话 id，**唯一**，外键 `ON DELETE CASCADE` |
| `anchor_message_id` | 建卡那一轮的助手消息 id，仅接口兼容 / 历史数据，不参与排版 |
| `title` | 标题，最长 200 字 |
| `items` | JSON 数组，每项 `{id,text,status,done,done_at,updated_at}` |
| `version` | 乐观锁版本号，成功写入 +1 |
| `last_run_id` | 最近一次成功写卡的运行 id |
| `created_at` / `updated_at` | 时间戳 |

写入使用独立会话 + 乐观锁重试（最多 3 次），卡片写失败只记日志，不影响消息落库。

### 5.2 合并语义

| 操作 | 规则 |
| --- | --- |
| `create` 无卡 | 新建，有效项 2～20 项，每项必须有文本 |
| `create` 有卡 | 按 `id` 重规划；旧项 `completed` 保持；旧项非终态按新块状态走；新块没有的 id 删除 |
| `update` | 无卡忽略；未知 id 忽略；`completed` 不回退；`pending ↔ in_progress` 可切换；同一 id 重复以最后一次为准 |
| 项数 | 超过 20 项整块忽略 |
| 无变化 | 不写库、不 bump `version` |
| 失败 | 保持上一次已提交状态，不猜测、不修补 |

### 5.3 幂等与并发

| 通道 | 幂等键 | 说明 |
| --- | --- | --- |
| 围栏 | `last_run_id` | 同一轮重复应用直接返回旧卡 |
| MCP | `context_id + 内容` | 一轮允许多次更新；内容相同返回 `changed=False` |
| 内核快照 | `last_run_id` | 与围栏一样一轮只应用一次 |

**不能拿 `last_run_id` 做 MCP 幂等**：一轮里会多次调用（建计划、完成第一步、完成第二步），
按 run 跳过会把后面的更新全吞掉。

## 6. 安全与部署边界

| 项 | 做法 |
| --- | --- |
| 令牌 | 每轮 256 位随机熵，前缀 `tc_`，只存哈希在内存，不写日志 |
| 凭据文件 | 对话家目录下 `task-card/context-<hash>/auth.json`，目录 0700、文件 0600，轮末删除 |
| 路径 | 只用 `sha256(context_id)` 拼路径，不用模型传入的原始字符串 |
| 请求体 | 字段白名单，多余字段直接 422 |
| 归属 | `conversation_id` 只来自 binding；`owner_id` 只用于断言与日志 |
| 运行校验 | binding 对应的 run 必须仍在注册表且未结束 |
| 限流 | 每 context 最多 120 次调用，超限 429 |
| 客户端入口 | 不提供面向浏览器的卡片写接口；内部接口 `include_in_schema=False` |

部署约束：**单进程**。binding 与令牌哈希在进程内存；多 worker 部署必须迁移到共享存储
（数据库或 Redis），或使用粘性会话。当前服务按单进程运行。

## 7. 开关与代码位置

- 开关：`CODA_TASK_CARD_MCP`，默认关闭。关闭时不注入 MCP server、不生成 context、
  内部接口不签发令牌，行为回退到纯围栏通道。
- 内置 MCP 声明：`backend/app/builtin_mcp.py` 的 `TASK_CARD`（`assignable=False`，
  只在「MCP」页展示，不允许用户分配 / 编辑）。
- 脚本：`scripts/mcp/task_card_mcp_server.py`，随 `scripts/mcp` 整目录打包。

| 层 | 文件 |
| --- | --- |
| 协议解析 / 合并 / 落库 | `backend/app/runtime/task_cards.py` |
| 每轮绑定 / 令牌 / 凭据 | `backend/app/runtime/task_card_mcp.py` |
| 内部写入口 | `backend/app/api/task_cards_internal.py` |
| 运行接线 | `backend/app/runtime/service.py` |
| MCP 物化 | `backend/app/runtime/mcp.py` |
| 内置声明 | `backend/app/builtin_mcp.py` |

### 8.2 常见问题

| 现象 | 先看什么 |
| --- | --- |
| 卡片不出现 | 这轮是否多步任务？是否有卡？内核是否 MCP？协议块是否被正确解析？ |
| 卡片停在上一状态 | 消息是否成功提交？`status` 是否为 `complete`？写卡是否冲突重试失败？ |
| MCP 内核没有卡片 | `CODA_TASK_CARD_MCP` 是否打开？适配器是否 `mcp=True`？凭据文件是否写入？ |
| 工具调用报 409 | 本轮是否先 `create`？`context_id` 是否是本轮输入里给出的？ |
| 工具调用报 429 | 本轮是否死循环刷调用（上限 120 次）？ |
| 卡片里出现协议 JSON | 检查 `strip_task_card*` 与 `stripTaskCardFence` 是否都执行。 |

## 9. 已知边界

- 内核任务工具桥接是有损兜底，不是权威同步；依赖、父子、优先级暂不建模。
- MCP 通道只覆盖声明 `mcp=True` 的内核，其余内核继续用围栏。
- 卡片不提供手动编辑，模型写坏后只能等下一轮修正。
- 多 worker 部署暂不支持 MCP 通道（binding 不共享）。
- 内核长驻进程可能缓存旧工具列表；启用开关后建议重启内核进程。
