# 技能版本管理方案

> 状态：**方案，尚未开工**。
> 适用对象：需要让 AI 定期「完善技能」、又不想把安全性寄托在 AI 自觉上的使用者；以及要实现这套机制的工程师。
>
> 事实基线：Coda `main` 分支当前工作区。**代码是唯一事实来源**；本文与代码冲突时以代码为准。
>
> 相关文档：`docs/功能文档/skills-mechanism.md`（技能机制现状）、`docs/功能文档/admin-mcp.md`（管理 MCP 工具表）。

---

## 1. 当前技能的设计

### 1.1 技能是什么

一个技能 = 一个目录，里面必须有 `SKILL.md`（frontmatter 元数据 + 正文说明书），可选带 `scripts/`、`references/` 等附属文件。目录名（slug）就是内核调用技能时用的名字。

### 1.2 两类技能、五个来源

| 类别 | 来源（`source_kind`） | 归谁管 | 能写吗 |
| --- | --- | --- | --- |
| 共享技能 | `system`（内核自带） | 内核自己 | ❌ 只读 |
| 共享技能 | `plugin`（已装插件里的） | 插件管理器 | ❌ 只读 |
| 共享技能 | `user` / `project`（宿主机扫到的） | 宿主机主人 | ✅ |
| 用户技能库 | `user`（导入）、`market`（市场装的） | 当前用户 | ✅ |
| 用户技能库 | 挂载到别的内核的引用 | 当前用户 | ✅（摘引用） |

### 1.3 数据模型

| 表 / 文件 | 作用 |
| --- | --- |
| `skills` | 统一编目：每「内核 × slug × 归属」一行，`path` 指向唯一实体，`fingerprint` 记内容指纹 |
| `agent_skills` | 分配表（多对多）：智能体 → 技能 |
| `skill-libraries/<owner>/.mounts.json` | 引用登记：哪些内核共享这份实体 |

关键事实：**一份用户技能实体只存一份**，被 N 个内核引用时 `skills` 表展开成 N 行，所有行共享同一个 `path`。

### 1.4 生命周期四环节

```
扫描编目（skills 表） → 分配（agent_skills） → 物化（agent-homes/<对话id>/<home>/skills/） → 内核隔离目录
```

物化的两条路径：

- **快速路径**：manifest 的条目（slug + 源路径 + 逐文件 size/mtime）与磁盘都没变 → 复用；
- **慢路径**：`rmtree` 受管目录后重建，**同盘优先硬链接**（零拷贝），不支持时降级普通复制。

### 1.5 写入路径盘点（现状）

平台自己只有这几条会改技能内容的路径：

| 动作 | 位置 | 行为 |
| --- | --- | --- |
| 导入 zip | `runtime/skills.py:import_skill_archive` | 解压覆盖 |
| 市场安装 / 重新安装 | `skillhub.py:extract_skill_archive` | **`rmtree` 旧目录后重写**（`:320`） |
| 挂载到别的内核 | `runtime/skills.py:copy_skill` | 首次收进库，之后只登记引用 |
| 删除 | `api/skills.py:delete_skill` | 摘引用 / 删目录 |

**没有“更新内容”的接口**：技能 API 只有 列表 / 重扫 / 导入 / 详情 / 导出 / 挂载 / 删除，没有 PUT / PATCH。

### 1.6 现有的“版本”能力

| 能力 | 现状 |
| --- | --- |
| frontmatter `version` 字段 | 仅作者手填，平台只存不校验、不据此判断 |
| `skills.fingerprint` | 记内容指纹，但**只用于幂等/去重判断**，重扫后旧值被覆盖 |
| 历史版本 | **不存在** |
| 变更归属 / 审计 | **不存在** |
| 回滚 | **不存在** |

### 1.7 两个关键缺口

**缺口 A：更新即销毁。**
市场“重新安装”是 `rmtree` + 重写，旧内容不留任何副本；导入覆盖同理。上游发版一出问题，**没有回退路径**。

**缺口 B：指纹不认内容。**
`agents/skills.py:462` 的 `_fingerprint()` 只计算「正文 + 每个文件的 `路径:大小`」：

```python
digest = sha1(text)
for item in files:
    digest.update(f"{item.path}:{item.size}")
```

**文件内容变了而大小没变（例如改了一行等长文本、换了同长度脚本），指纹不变**，平台会认为「没变」。这会让任何版本检测逻辑失效。

> 补充：`backend/data/` 已被 `.gitignore` 排除，源码 git 对用户技能库**没有任何覆盖**。

## 2. MCP 机制存在的问题

### 2.1 能力盘点：只有“看”和“删”

管理 MCP（`scripts/mcp/coda_admin_mcp_server.py`）与技能相关的工具：

| 工具 | 能力 | 说明 |
| --- | --- | --- |
| `skill_list` | 读 | 列表 |
| `skill_get` | 读 | 详情，**正文超 2000 字截断** |
| `skill_rescan` | 触发扫描 | 不改内容 |
| `skill_delete` | 删 | 需 `confirm` |

**没有 `skill_update` / `skill_write` / `skill_apply` 之类的写工具。** 后端也没有对应的写接口。

### 2.2 结论：AI 改技能，根本不走 MCP

既然 MCP 没有写入口，所谓“MCP 直接对应技能源头文件”不成立。AI 只能走一条野路子：**直接改磁盘文件**（shell / 编辑器）。

### 2.3 野路子的两种结局，都很糟

AI 运行时看到的是**物化副本**（`agent-homes/<对话id>/<home>/skills/`），不是源目录。而副本与源文件之间可能是**硬链接（共享 inode）**——实测 `multi-search-engine/SKILL.md` 的硬链接数为 9。

于是 AI 改文件只有两种结果：

1. **原地改写** → 共享 inode，**源目录跟着被改**，平台毫不知情；
2. **写新文件再替换** → 只改了临时副本，下一轮物化重建**被覆盖**，白改。

### 2.4 平台感知不到

变化检测只发生在：启动重扫、手动「重新扫描」、导入/挂载/删除之后。**没有文件监听，也没有定时巡检。** AI 在两次扫描之间改了几次，平台既不知道次数，也没有中间版本。

### 2.5 无归属、无审计、无恢复

- 不知道是谁改的、哪次对话改的；
- 改坏了没有回滚；
- 删除技能直接丢内容，不可恢复。

### 2.6 小结

| 问题 | 后果 |
| --- | --- |
| 无写通道 | AI 只能绕开平台改文件 |
| 硬链接共享 | 改副本可能污染源；改动也可能被覆盖丢失 |
| 无巡检 | 变更不可见、不可归因 |
| 无存储 | 旧版本无处可留、无从恢复 |

## 3. 用户痛点

### 3.1 真实场景

> 我写了一批自己的技能，让 AI 定期去“完善”。一旦它改坏了，或者越改越差，我想退回上一版。

### 3.2 痛点清单

1. **历史版本完全依赖 AI 自觉**——它不提交、不报版本号，就没有记录。
2. **更新是破坏性的**——市场更新 / 导入覆盖直接销毁旧内容，无法回退。
3. **不知道改了什么**——没有版本对比，只能靠回忆。
4. **不知道谁改的**——AI 改的还是我改的，说不清。
5. **改动可能根本落错了地方**——硬链接导致“改了副本、脏了源头”或“改了副本、白改”。
6. **一份技能多内核共用**——一次更新全平台生效，爆炸半径大，却无法让某个智能体先留在旧版。
7. **删除即永久丢失**。

### 3.3 反面需求（明确不要的东西）

- ❌ 不要依赖 AI 主动提交 / 主动写 commit；
- ❌ 不要复用源码 git（技能不该进代码仓库）；
- ❌ 不要“另建一个 git 仓库”这种只等于备份的方案；
- ❌ 不要把每个对话的物化副本都备份（会撑爆磁盘）；
- ❌ 不要给 `system` / `plugin` 技能做版本（平台管不到内核的写入）。

## 4. 解决方案

### 4.1 设计目标与原则

| 原则 | 含义 |
| --- | --- |
| **强制记录，不靠自觉** | 版本由平台在写入路径上自动产生 |
| **内容寻址，天然去重** | 只存变化的文件，多版本几乎不额外占空间 |
| **只增不改** | 回滚也是“新增一条版本”，历史不可篡改 |
| **可归因** | 每条版本带来源、操作者、运行 id、时间 |
| **可回滚 / 可对比 / 可钉住** | 面向用户的三件实事 |
| **可清理** | 保留策略 + 磁盘上限，不无限膨胀 |
| **跨平台** | 纯 Python，不依赖 git 二进制 |

### 4.2 总体架构

```
         平台写入路径                 外部直接改文件
   导入 / 市场 / 挂载 / 删除        AI 用 shell / 编辑器
              │                          │
              ▼                          ▼
      ┌───────────────────────────────────────┐
      │       版本服务 skill_versions          │
      │  记录 · 检测 · 回滚 · 对比 · 清理 · 钉住 │
      └───────────────┬───────────────────────┘
                      │
      ┌───────────────▼───────────────────────┐
      │  内容寻址存储 skill-store/             │
      │  blobs/<sha256>  +  versions/<清单>    │
      └───────────────┬───────────────────────┘
                      │
      ┌───────────────▼───────────────────────┐
      │  SQLite: skill_versions（账本）        │
      └───────────────────────────────────────┘
```

### 4.3 数据模型

新增表 `skill_versions`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | TEXT PK | 版本 id（uuid） |
| `owner_id` | TEXT NULL | 归属用户；共享技能为空 |
| `slug` | TEXT | 技能名（实体维度，不是内核维度） |
| `version_no` | INTEGER | 同一技能内自增：1,2,3… |
| `fingerprint` | TEXT | 清单的 sha256（真正的版本指纹） |
| `manifest_path` | TEXT | 版本清单文件路径 |
| `source` | TEXT | `import` / `market` / `copy` / `manual` / `ai` / `rollback` |
| `actor_id` | TEXT NULL | 用户 id 或智能体 id |
| `run_id` | TEXT NULL | 触发本次变更的运行 id |
| `note` | TEXT NULL | 备注（如“回滚自第 2 版”） |
| `pinned` | BOOLEAN | 钉住则永不自动清理 |
| `total_bytes` | INTEGER | 该版本新增 blob 的字节数 |
| `created_at` | DATETIME | 时间 |

可选：`agent_skills.version_no`（NULL = 跟随最新），用于钉版本。

### 4.4 磁盘布局

```
<数据目录>/skill-store/
├── blobs/
│   └── 3f/8a/3f8a...e1        # 文件名 = 内容 sha256，天然去重
└── versions/
    └── <owner>/<slug>/
        ├── 0001.json          # {"SKILL.md": "<sha>", "scripts/run.sh": "<sha>"}
        └── 0002.json
```

约束：

- blob **必须是真拷贝**，不能硬链接到活目录（活目录可能被外部原地改写，会把 blob 一起改坏）；
- 存储根在数据目录下，**不进入任何技能根**，避免被扫描或物化；
- 版本实体按 `(owner_id, slug)` 归属，**与内核类型无关**（一份实体多内核共用）。

### 4.5 核心流程

**① 记录版本 `record_version()**
遍历技能目录（跳过 `SKIP_DIRS` 与隐藏目录）→ 每个文件算 sha256 → 缺失的 blob 写入 → 生成清单 → 插入记录。已有 blob 直接复用。

**② 变化检测**
三个触发点，缺一不可：

| 触发点 | 位置 | 覆盖场景 |
| --- | --- | --- |
| 平台写入路径 | 导入 / 市场 / 挂载 / 复制 | 平台自己的更新 |
| 重扫时指纹变化 | `runtime/skills.rescan` | 启动、手动重扫 |
| 后台定时巡检 | 新增 asyncio 循环（默认 30s） | **AI 直接改磁盘** |

> 已知限制：两次巡检之间的多次写入只会保留“最后一次之前”的内容。可通过“每次运行结束立即巡检”缩小窗口。若需严格逐次捕获，后续可加文件监听（`watchdog`），作为可选增强。

**③ 回滚 `restore_version()`**
按清单把 blob 拼到暂存目录 → 原子替换当前目录 → **再记一条新版本**（`source=rollback`，`note=回滚自第 N 版`）→ 重扫 → 下一轮物化自动重建。历史只增不改。

**④ 对比 `diff_versions()`**
清单相减得到 新增 / 删除 / 修改 文件列表；文本文件再算 unified diff。内容寻址让这一步零成本。

**⑤ 清理 `prune_versions()`**
保留：最近 N 版（默认 20）+ 所有 `pinned` + 老版本按天抽样 1 份。删除清单与无人引用的 blob。支持每用户磁盘上限（默认 200MB），超限先删最老的非钉住版本。

**⑥ 钉版本（第二阶段）**
`agent_skills.version_no` 非空时，物化按该版本清单拼装，而不是取当前源目录。这才是“历史对话复现当时内容”的成立条件。

### 4.6 指纹修复（地基，必须同批做）

把 `agents/skills.py:_fingerprint()` 升级为：**每个文件的内容 sha256 的稳定排序拼接**，再取整体哈希。理由：

- 现有算法只看 `路径:大小`，等长改动会漏检；
- 版本记录的“是否有变化”完全依赖它；
- 顺带让 `skills.fingerprint` 具备跨机可复现性。

### 4.7 MCP 写通道与写保护（第二阶段）

**给 AI 开一扇正规的门，把野路子堵上：**

1. 新增 MCP 工具 `skill_update`：提交 `slug` + 新 `SKILL.md`（或补丁）+ `confirm`；
2. 平台处理顺序：**先存档旧版 → 校验 → 写源目录 → 重扫 → 返回新版本号**；
3. 技能源目录对 AI **只读**（含物化副本不硬链接“允许 AI 改”的技能，或明确不暴露源路径）；
4. 所有后台任务改技能都必须走这个入口。

只有到这一步，“版本记录”才算**强制**而非**兜底**。

### 4.8 API 与界面

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/skills/{id}/versions` | 版本列表（含来源、操作者、时间、大小） |
| GET | `/api/skills/{id}/versions/{vid}` | 版本详情（文件清单） |
| GET | `/api/skills/{id}/versions/{vid}/diff` | 与当前或指定版本对比 |
| POST | `/api/skills/{id}/versions/{vid}/rollback` | 回滚（生成新版本） |
| GET | `/api/skills/{id}/versions/{vid}/export` | 导出该版本 zip |
| POST | `/api/skills/{id}/versions/{vid}/pin` | 钉住 / 取消钉住 |

界面：技能详情页新增「历史版本」面板，列表 + 对比 + 下载 + 回滚。

### 4.9 分阶段实施

| 阶段 | 内容 | 预估 | 交付物 |
| --- | --- | --- | --- |
| P0 | 指纹升级为内容哈希 | 0.5 天 | 变更可被真实检测 |
| P1 | 版本表 + 全量目录快照（先跑通接口） | 1 天 | 自动留版、列表、回滚 |
| P2 | 底层换内容寻址 + 清理策略 | 1.5 天 | 去重、省空间、自动清理 |
| P3 | 对比 + 前端历史面板 | 1.5 天 | 可视化版本管理 |
| P4 | MCP `skill_update` + 源只读 | 2 天 | 从“兜底”升级为“强制” |
| P5 | 钉版本 + 按版本物化 | 2 天 | 单智能体锁版本 |

> P1 的接口与 P2 的存储引擎解耦：先定契约，后换发动机，界面与 API 不用改。

### 4.10 验收标准

- [ ] AI 直接改磁盘上的 `SKILL.md`，30 秒内出现新版本记录；
- [ ] 等长内容修改也能被识别（指纹修复）；
- [ ] 市场重新安装后，旧版本仍可回滚；
- [ ] 回滚生成新版本，历史可追溯，不覆盖原记录；
- [ ] 两个版本可对比出具体变化的文件与行；
- [ ] 清理策略生效：非钉住版本按数量与容量双重收敛；
- [ ] 现有技能分配、物化、快速路径行为不变（回归测试全绿）。

### 4.11 风险与对策

| 风险 | 对策 |
| --- | --- |
| 巡检间隔内多次写入只留最后一版 | 运行结束即巡检；后续可选文件监听 |
| blob 与活文件被硬链接污染 | blob 一律真拷贝，禁止硬链接 |
| 磁盘膨胀 | 内容寻址 + 保留策略 + 每用户上限 |
| 外部进程并发写导致读到半截文件 | 写入用“暂存目录 + 原子替换”；读取时容忍失败并重试 |
| 删除技能后版本成为孤儿 | 技能删除后版本保留 30 天再随清理回收 |
| 平台写入与巡检并发 | 按 `(owner, slug)` 加进程内锁 |

### 4.12 非目标

- 不做跨用户共享历史（按 `owner_id` 隔离）；
- 不为 `system` / `plugin` 技能建版本（内核写入平台无法拦截）；
- 不追求 git 级别的分支 / 合并；
- 不把版本数据放进源码仓库。

### 4.13 为什么不用 git 做后端

| 理由 | 说明 |
| --- | --- |
| 更新会删掉仓库 | 市场更新是 `rmtree` 整个技能目录，`.git` 一起没 |
| 仓库只能放外面 | 放外面就退化成“另建备份目录”，平台拿不到语义 |
| 仍然要人/AI 提交 | 又回到“靠自觉”，没解决根因 |
| 桌面端未必有 git | 部署面变窄 |
| 不支持钉版本 / 归因 / 物化联动 | 这恰恰是用户真正要的部分 |

结论：**git 解决“文件历史”，本方案解决“技能版本治理”。** 二者不是一回事。

---

## 5. 一页总结

- **现状**：技能更新是破坏性的，平台无历史、无归属、无回滚；指纹还认不出等长改动。
- **MCP**：只有读和删，没有写；AI 改技能全靠直接改磁盘，且硬链接会让改动要么污染源、要么白改。
- **痛点**：用户让 AI 定期完善技能，安全却寄托在 AI 自觉上。
- **方案**：内容寻址版本库 + 写入路径强制记录 + 定时巡检兜底 + 回滚/对比/清理，第二阶段补 MCP 写通道与源目录只读，把“兜底”升级为“强制”。
