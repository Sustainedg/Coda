# 统一内容存储设计方案

> 适用对象：要在 Coda 里让 AI 产出 / 复用「文档、报告、笔记、数据集」这类**内容**，并希望
> 「内容只存一份、项目侧只放索引」的产品与工程同学。
>
> 事实基线：仓库 `main` 分支当前工作区（`/vol1/1000/同步库/python/项目/Bot`）。**代码是唯一事实来源**，
> 本文与代码冲突时以代码为准。文内所有结论都标注了仓库内路径（多数到行号），可逐条抽查。
>
> 相关文档：`docs/功能文档/admin-mcp.md`（系统管理 MCP 现状）、`docs/架构/architecture.md` §5（技能机制）、
> `docs/计划任务/skills-versioning-plan.md`（内容寻址存储的既有先例）。

---

## 0. 摘要

1. **现状**：仓库里的「coda 管理 MCP」= `scripts/mcp/coda_admin_mcp_server.py`，是一个 stdio 传输、
   仅用标准库、把平台 REST API 包成 **22 个工具**的内置服务器。它是**平台管理面**（智能体 / 协作组 /
   技能 / MCP / 网关），**不含任何内容 / 文件 / 文档存取工具**（检索证据见 §1.6 与 §8）。
2. **平台当前没有「内容库」这个概念**：`backend/app/models.py` 里没有 Project / Document / FileStore
   之类的表；内容的实际落点是**对话工作目录里的普通文件**（`attachments/`、`generated-images/`），
   以及技能库（`skill-libraries/<owner>/<slug>`）。
3. **推荐方案**：**中央内容库（按 owner 隔离的内容寻址存储）+ 项目侧索引**。内容字节只存一份
   （`objects/<sha256>`），逻辑文档身份（`documents`）、版本（`document_versions`）、
   项目归属（`project_contents`）都在 SQLite；项目侧只放引用与元数据，不复制正文。
4. **关键未决**：平台**没有「项目」实体**（只有智能体分组 `group_name` 与协作组）。
   项目边界怎么定义必须产品拍板，本文给了最小可行的 `projects` 表草案（§2.3）与两个备选口径（§7.2）。

### 1.7 现状的能力缺口

1. **没有内容身份**：文件靠路径标识。同名不同内容会覆盖（`attachments` 用随机串规避，但没有语义）；
   同一内容换个名字就是两份。
2. **没有去重**：同一张 10 MB 的图进 5 个对话 = 5 份字节；平台没有任何跨对话的内容索引。
3. **没有版本**：`attachments` / `generated-images` 是就地写；技能那边已经吃过「更新即销毁」的教训
   （`docs/计划任务/skills-versioning-plan.md:73-87`）。
4. **没有检索**：只有「知道相对路径才能读」（`attachments.resolve_workspace_file`），
   无法按项目 / 标签 / 时间 / 内容找东西。
5. **AI 没有正规写入口**：coda-admin 没有写内容的工具，AI 只能「用 shell 直接改工作目录」——
   平台看不见、无法治理（同上文档 `:106-120` 的结论完全适用）。

## 2. 存储层设计

### 2.1 目标与不变量

| # | 不变量 | 说明 |
| --- | --- | --- |
| I1 | **内容字节只存一份** | 同一 `(owner_id, sha256)` 只对应一个对象文件；N 个文档 / N 个项目引用它 |
| I2 | **对象不可变** | 写入即定稿；改内容 = 新对象 + 新版本，绝不原地改写 |
| I3 | **数据库是权威源** | 项目侧 `index.jsonl` 与 `files/` 只是**派生视图**，可随时重建 |
| I4 | **按 owner 隔离** | 对象目录按 `owner_id` 分桶；**不做跨用户去重**（避免存在性探测与删除语义纠缠） |
| I5 | **失败即无副作用** | 写入走「暂存 → 校验 → 原子 rename → 事务提交」，任一步失败不落半成品 |
| I6 | **可回滚** | 老路径（工作目录里的文件）在迁移完成并验证前**一律保留原样** |

### 2.2 目录与命名规则

```
<数据目录>/content-store/                 # 与 skill-libraries / agent-homes 平级（backend/app/settings.py:25 的 data_dir 下）
├── <owner_key>/                          # owner_key 复用 backend/app/runtime/skills.py:88 的 owner_key()（空 owner → "local"）
│   ├── objects/
│   │   └── 3f/8a/3f8a…e1                # 文件名 = 内容 sha256 全 64 位；前 2+2 位分两级目录防单目录爆炸
│   ├── projects/
│   │   └── <project_slug>/
│   │       ├── index.jsonl               # 派生索引：每行一条引用（doc_id / slug / version / hash / tags）
│   │       └── files/                    # 可选：只读硬链接视图（doc_slug@v3.md），不给也不影响功能
│   ├── tmp/                              # 写入暂存（与 objects 同盘 → os.replace 原子）
│   └── gc.log                            # 回收审计（追加写，谁删了哪个对象、为什么）
```

命名规则（每条都能落到实现里）：

| 对象 | 规则 | 理由 |
| --- | --- | --- |
| 对象文件名 | `sha256(内容字节)` 全 64 位十六进制，无扩展名 | 内容即身份，天然去重；扩展名进 DB 的 `mime`，同一字节换文件名不会产生第二份 |
| 分片目录 | `hash[0:2] / hash[2:4]` | 单目录最多 256 个子目录、每个再 256 个，百万级对象也不退化 |
| 文档 id | `doc_<uuid4 hex>` | 与内容解耦：内容变了 id 不变（引用稳定） |
| 版本号 | 每个文档内自增 `1,2,3…` | 人类可读，`UNIQUE(document_id, version_no)` |
| 项目 slug | `^[a-z0-9][a-z0-9-]{0,39}$`，与 owner 内唯一 | 要进路径，必须可预测且无穿越风险；显示名另存 `name` |
| 暂存文件 | `tmp/<uuid4>.part` | 写一半的垃圾不会被当成对象（`objects/` 下只出现完整且校验过的文件） |

> 复用既有纪律：`skill-libraries` 已经是「按 owner 分目录、单一实体、引用登记在同级 JSON」的形态
> （`backend/app/runtime/skills.py:99-118`、`backend/app/models.py:285-292`），本设计只是把它从「技能」推广到「任意内容」。
> 同时**沿用** `docs/计划任务/skills-versioning-plan.md:236-240` 的教训：blob 必须是**真拷贝**，不能硬链接到
> 「活目录」—— 活目录会被外部就地改写，硬链接会把 blob 一起改坏。

### 2.3 数据模型（新增表，均登记 `ADDITIVE_COLUMNS` 之外的新表，由 `create_all` 自动建）

| 表 | 关键字段 | 约束 / 索引 | 作用 |
| --- | --- | --- | --- |
| `projects` | `id`、`owner_id`、`slug`、`name`、`root_dir`（可空，联动某个工作目录）、`created_at`、`deleted_at` | `UNIQUE(owner_id, slug)`；`index(owner_id)` | 内容的归属容器（**唯一需要产品确认的概念**，见 §7.2） |
| `content_objects` | `owner_id`、`hash`、`size`、`mime`、`refcount`、`created_at`、`last_verified_at` | `PK(owner_id, hash)` | 物理内容（一行 = 一个 blob 文件） |
| `documents` | `id`、`owner_id`、`project_id`、`slug`、`title`、`kind`、`current_version_no`、`meta`(JSON)、`created_at`、`updated_at`、`deleted_at` | `UNIQUE(project_id, slug)`；`index(owner_id)`、`index(project_id)` | **逻辑文档**（身份），改名 / 新版本都不换 id |
| `document_versions` | `id`、`document_id`、`version_no`、`object_hash`、`source`、`actor_id`、`agent_profile_id`、`run_id`、`conversation_id`、`note`、`created_at` | `UNIQUE(document_id, version_no)`；`index(object_hash)` | 版本账本（只增不改） |
| `project_contents` | `project_id`、`document_id`、`role`(`primary`/`reference`)、`added_by`、`added_at` | `PK(project_id, document_id)` | 项目侧**引用**（这就是「项目只放索引」的落点） |
| `content_tags` | `document_id`、`tag` | `PK(document_id, tag)`；`index(tag)` | 标签检索（比在 JSON 里搜可靠得多） |
| `content_fts`（可选） | FTS5 虚表：`document_id`、`title`、`summary`、`body`，`tokenize='trigram'` | 与 `documents` 一对一手工同步 | 全文检索（中文必须用 trigram，见 §4.4） |

设计要点：

- **`documents` 与 `content_objects` 是两套身份**：前者是「这篇东西」，后者是「这堆字节」。
  同一份字节被 3 篇文档引用时，`content_objects.refcount=3`，磁盘仍只有 1 份（I1）。
- **`document_versions` 持有 `object_hash` 而不是复制正文**：历史版本天然零成本（内容寻址的副产品，
  与 `docs/计划任务/skills-versioning-plan.md:262` 的 diff 思路一致）。
- **`project_contents` 允许一份文档进多个项目**（`role=reference`）：这是「归属模型」能成立的前提，
  也解释了为什么「项目侧只放索引」不等于「一份内容只属于一个项目」。
- 新增列（若要给 `conversations` 加 `project_id`）必须登记 `models.py` 的 `ADDITIVE_COLUMNS`
  （定义在 `backend/app/models.py:43`，范例见 `:106` 的 `mcp_servers`），旧行容忍空值。

### 2.4 写入、去重与幂等

```
content_put(owner, project, title, kind, bytes)
  │
  ├─ 1. 校验：owner 有该项目；title/kind 合法；大小在限；文本编码 UTF-8
  ├─ 2. hash = sha256(bytes)
  ├─ 3. 查 content_objects(owner, hash)
  │      ├─ 命中 → 不写字节（秒传 / 去重），refcount 稍后随版本 +1
  │      └─ 未命中 → 写 tmp/<uuid>.part → 读回校验 sha256 → os.replace 到 objects/ab/cd/<hash>
  ├─ 4. 解析文档身份：给了 doc_id/slug 且已存在 → 追加新版本；否则新建 documents 行
  ├─ 5. 插 document_versions(version_no = max+1, object_hash)，更新 current_version_no
  ├─ 6. upsert project_contents / content_tags / content_fts
  └─ 7. 提交事务；失败则回滚并把刚写的孤儿对象留给 GC（宽限期后回收）
```

| 策略 | 规则 |
| --- | --- |
| 去重键 | `(owner_id, sha256(内容))`；**不跨用户** |
| 去重边界 | 去重只发生在「字节」层；标题 / 标签 / 项目归属各自独立，互不合并 |
| 幂等 | 可选 `idempotency_key`（同 owner 内 `UNIQUE`，建议用 `run_id + 序号`）：重试不产生第二版 |
| 内容校验 | 写入后**读回再算一次 sha256**（防磁盘/链路静默损坏）；不符即删暂存文件并报错 |
| 原子性 | 同盘 `os.replace`；跨盘部署时 `tmp/` 必须与 `objects/` 同挂载点（不支持则退化为「写完再 rename 到临时名」） |
| 上限 | 单对象 ≤ 32 MB（与 `backend/app/image_ingest.py:24` 的 `MAX_IMAGE_BYTES` 对齐）；单次文本 ≤ 2 MB；超限请走「引用工作目录文件」的 `content_put_file` |
| 并发 | 进程内按 `(owner, document_id)` 加 `asyncio.Lock`；DB 侧靠 `UNIQUE(document_id, version_no)` 兜底重试 |

### 2.5 版本管理与回收

| 项 | 设计 |
| --- | --- |
| 版本产生 | 每次写入一个新版本（`source` ∈ `ai` / `manual` / `import` / `scan` / `rollback`）；**从不覆盖** |
| 回滚 | `content_restore(doc, version_no)` = 以旧版本的对象为内容**追加一个新版本**（`source=rollback`，`note=回滚自第 N 版`），历史不动 |
| 保留策略 | 最近 20 版 + 全部 `pinned` 版本 + 更老版本按天抽样 1 份（与 `docs/计划任务/skills-versioning-plan.md:265` 完全一致，避免两套心智模型） |
| 对象回收 | `refcount=0` 且 `last_verified_at` 超过 30 天的对象才可删；GC 先写 `gc.log` 再删文件，删除后校验目录项 |
| 软删除 | `documents.deleted_at` 非空即从列表消失；仍被**未删除**引用持有时不物理删（与网关/凭据的软删除纪律一致，`AGENTS.md` §3.6） |
| 完整性巡检 | 低频（默认每天）抽样 1% 对象校验 sha256；不符则标记 `corrupt` 并在检索结果里降级提示，不静默返回坏内容 |
| 备份 | `backend/data/` **不在 git**（`.gitignore:13`），因此迁移前必须文件级备份（`cp -a data data.bak-<日期>`），由运维脚本保证 |

### 2.6 与「工作目录」的关系（避免第二套文件系统）

- 工作目录仍是 AI 的**操作面**（它能直接读写文件，这是内核能力，平台拦不住）；
- 内容库是**权威面**：AI 通过 MCP 工具写入的内容才进库；直接写工作目录的文件在对账扫描时
  被识别为 `source=scan` 导入（§5.2 的 P2）；
- 项目侧可选 `files/` 硬链接视图供 `ls` / `grep` 用；因为对象不可变（I2），硬链接是安全的；
  但**任何就地改写都会污染对象**，因此 `files/` 下的一律 `chmod 0444`，并纳入巡检。

## 3. 归属模型

### 3.1 推荐模型定义：**内容只存一份，项目侧只放索引 / 引用与元数据**

**定义（可直接当验收口径）**：

> 一份内容（同一 `owner_id` 下字节完全相同的对象）在磁盘上**只存在一个文件**
> （`content-store/<owner>/objects/<sha256>`）。项目不持有正文副本，只持有两类东西：
> ① **引用**：`project_contents(project_id, document_id, role)` 指向文档；
> ② **元数据**：文档级（标题 / kind / tags / summary）与项目级（加入时间、角色、钉住的版本）。
> 因此「同一内容出现在 N 个项目」= 1 份字节 + N 行引用；删除某个项目的引用**不影响**其它项目，
> 只有最后一个引用与全部版本都消失、且过了宽限期，字节才可能被回收。

形式化不变量：

| 编号 | 不变量 | 可验证方式 |
| --- | --- | --- |
| O1 | `objects/<hash>` 的字节数 = 引用它的所有版本的内容字节数（不是 N 倍） | 磁盘统计 vs `content_objects.size` 求和 |
| O2 | 任意两个文档若 `object_hash` 相同，则它们指向同一个物理文件 | `SELECT hash, count(*) FROM content_objects GROUP BY hash HAVING count(*)>1` 应为空（PK 保证） |
| O3 | 项目目录里不存在正文副本（除非用户显式开启 `files/` 视图） | `du -sh projects/<slug>` 应 ≈ 0 |
| O4 | 删除一个项目 / 一条引用不会让其它项目的可读内容发生变化 | 回归用例：两项目共用一文档，删一个，另一个仍可读可下载 |

图示：

```
                  ┌──────────────────────────────┐
   AI 写入 ──────▶│ objects/3f/8a/3f8a…e1 (1 份) │◀────── 版本 1..N 都指向它
                  └──────────────┬───────────────┘
                                 │ document_versions(object_hash)
                        ┌────────▼─────────┐
                        │ documents(doc_…) │  ← 逻辑身份（标题/kind/tags）
                        └────────┬─────────┘
              ┌──────────────────┼──────────────────┐
              │                                     │
   project_contents(项目 A, role=primary)   project_contents(项目 B, role=reference)
              │                                     │
      projects/A/index.jsonl                 projects/B/index.jsonl
        （只有指针与元数据，无正文）          （只有指针与元数据，无正文）
```

### 3.2 备选模型一：**全量复制**（每个项目各存一份实体）

每个项目在自己的目录里放一份完整副本，平台只负责编目与「同步」。

| 维度 | 表现 |
| --- | --- |
| 一致性 | 差：改一处要同步 N 处，没改到就出现两个版本分叉 |
| 存储 | 差：N 倍膨胀（大文件与图片尤其明显） |
| 删除 / 权限 | 差：一个项目删了不影响别人，但「哪份是准的」无人知道 |
| 离线 / 便携 | 好：项目目录拿起来就能用 |
| 实现 | 简单：几乎不用改现有「文件就在工作目录」的模型 |

### 3.3 备选模型二：**项目内嵌**（内容作为项目目录里的普通文件，平台只编目路径）

即「今天的行为」，把 `workspace` 当成项目，文件就是文件，平台只登记「哪个项目里有什么」。

| 维度 | 表现 |
| --- | --- |
| 一致性 | 中：单项目内天然一致；跨项目同一内容仍是两份 |
| 存储 | 差：无去重 |
| AI 友好 | 最好：内核本来就会读写文件，零学习成本 |
| 治理 | 差：AI 直接改磁盘，平台看不见（`docs/计划任务/skills-versioning-plan.md:110-120` 的两种结局原样复现） |
| 实现 | 最低：几乎零改造 |

### 3.4 备选模型三：**外链引用**（只存 URL / 路径，正文在别处）

| 维度 | 表现 |
| --- | --- |
| 一致性 | 差：内容不在平台手里，随时可能 404 / 被改 |
| 存储 | 最好：平台几乎不占空间 |
| 可用性 | 差：离线、内网、对方下线就裂（`backend/app/image_ingest.py:3-6` 已经为图片踩过这个坑并选择「抓回本地」） |
| 审计 / 版本 | 不可行 |

### 3.5 四种模型对比

| 模型 | 内容份数 | 一致性 | 磁盘成本 | 可治理性（版本/审计/权限） | 离线可用 | 改造量 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **单实体 + 项目索引（推荐）** | 1 | 强（单一事实源） | 最低 | 强 | 强（本地字节） | 中 | ✅ |
| 全量复制 | N | 弱 | N 倍 | 弱（同步逻辑本身是风险源） | 强 | 中 | ❌ |
| 项目内嵌 | 1（单项目内） | 项目内强、跨项目无 | 中（跨项目重复） | 弱 | 强 | 低 | ❌（作为过渡态保留） |
| 外链引用 | 0 | 弱 | 最低 | 无 | 无 | 低 | ❌（仅作补充：外部源可登记为 `role=reference` 的文档，正文仍抓回本地） |

### 3.6 混用规则（现实里必然混用，要写死边界）

| 场景 | 允许的模型 |
| --- | --- |
| AI 通过 MCP 产出的文档 / 报告 / 数据集 | 必须是「单实体 + 引用」 |
| 用户上传的大二进制（视频 / 模型权重） | 「单实体 + 引用」，但超过 32 MB 走「仅登记路径 + 哈希」的外链补充（正文不进库） |
| 遗留的工作目录文件 | 先「项目内嵌」原样保留，对账扫描后转为「单实体 + 引用」，原路径留 `legacy_path` 元数据 |
| 外部可访问的权威源（如公司 Wiki） | 允许 `role=reference` 的外链登记，但**不参与**版本与全文检索 |

## 4. AI 写入的元数据与检索

### 4.1 必填元数据（缺一即拒绝写入，`422`）

| 字段 | 类型 | 必填 | 取值示例 | 说明 / 校验 |
| --- | --- | --- | --- | --- |
| `project` | string（slug） | ✅ | `"bot"` | 必须是当前用户已存在的项目；不存在 → `422` 并列出可选 slug（与 `_resolve_agent` 的可操作错误同风格，`scripts/mcp/coda_admin_mcp_server.py:283-301`） |
| `title` | string | ✅ | `"MCP 存储调研"` | 1–200 字符；不合法就拒绝，不自动截断 |
| `kind` | enum | ✅ | `"spec"` | `spec`/`note`/`report`/`dataset`/`code`/`other`；用于列表分组与默认渲染 |
| `content` **或** `content_base64` **或** `source_path` | string | ✅（三选一） | `"# 标题\n正文…"` / `"iVBORw0…"` / `"reports/q3.md"` | `content` 为 UTF-8 文本；`content_base64` 为二进制；`source_path` 是**相对当前工作目录**的路径，服务端按 `attachments.resolve_workspace_file` 同等规则校验（`backend/app/attachments.py:84`） |
| `doc_slug` | string | ⬜（建议） | `"mcp-storage-research"` | 不给则由标题生成；同项目内唯一，用作路径与稳定引用 |
| `idempotency_key` | string | ⬜（重试时给） | `"run_ab12:1"` | 同 owner 内唯一；命中则返回已有版本，不产生第二版 |

### 4.2 可选元数据

| 字段 | 类型 | 示例 | 说明 |
| --- | --- | --- | --- |
| `summary` | string | `"调研 coda 管理 MCP 现状"` | ≤ 500 字；列表与检索结果**优先返回它**（省上下文，见 4.6） |
| `tags` | string[] | `["mcp","storage","design"]` | 每个 ≤ 40 字；写入 `content_tags` |
| `language` | string | `"zh"` | 影响全文分词器选择与默认渲染 |
| `mime` | string | `"text/markdown"` | 不给时按 `source_path` 后缀或魔数推断（参照 `backend/app/image_ingest.py:51-63`） |
| `supersedes_version` | integer | `3` | 显式声明「本次是第 3 版的更新」；与「最后版本」不符 → `409`（防并发覆盖） |
| `sensitive` | boolean | `false` | `true` 时**不进全文索引**（标题与标签仍可检索），检索结果只回摘要 |

### 4.3 由服务端填写、**模型不可自填**的元数据

| 字段 | 来源 | 为什么不让模型填 |
| --- | --- | --- |
| `owner_id` | 令牌所属用户（PAT） | 模型说「我是别人的」不算数 |
| `agent_profile_id` / `run_id` / `conversation_id` | 运行上下文注入的环境变量 | 这是归属与审计的唯一凭据，允许自填就能伪造 |
| `content_sha256` | 服务端对字节计算 | 客户端传的哈希只作为「秒传提示」，最终以服务端为准 |
| `created_at` / `version_no` | 服务端 | 时间与顺序必须由权威源决定 |

> 这条纪律与平台现有做法一致：coda-admin 的 `CODA_TOKEN` 与 `CODA_BASE_URL` 由平台托管、
> 模型看不见（`backend/app/builtin_mcp.py:176-195`）；凭据只以环境变量注入（`AGENTS.md` §7）。

### 4.4 检索方式

| 检索维度 | 入口 | 实现 | 备注 |
| --- | --- | --- | --- |
| 按项目 | `content_list(project=…)` | `project_contents` 索引 | 默认按 `added_at` 倒序 |
| 按标签 | `content_list(project=?, tag=…)` | `content_tags(tag)` 索引 + join | 多标签取交集 |
| 按时间 | `content_list(since=, until=)` | `documents.updated_at` | ISO8601，服务端按 UTC 比较 |
| 按内容哈希 | `content_put` 的秒传 + `content_get(hash=…)` | `content_objects` PK | 哈希是「同一份内容」的判定依据，唯一可靠 |
| 全文 | `content_search(q=, project=?)` | FTS5 虚表，`tokenize='trigram'` | **中文必须 trigram**：默认 unicode61 分词器不切中文，`MATCH` 基本查不出来 |
| 结构化字段 | `content_list(kind=, doc_slug=)` | 普通索引 | 常用组合建议 `index(project_id, kind)` |

> 实测记录（本机 SQLite 3.46.1）：`create virtual table … using fts5(title, body, tokenize='trigram')`
> 对「只存一份」「项目侧」这类中文子串可命中；**但 2 字查询（如「存储」）不命中** ——
> trigram 需要至少 3 个字符。因此 `content_search` 对 `len(q) < 3` 的查询必须回退到 `LIKE '%q%'`
> （带 `project_id` 限制，避免全表扫），并在结果里标注「本次为模糊匹配」。
> 若目标部署的 SQLite 无 FTS5，则整体回退 `LIKE`，功能不缺失、只是变慢（不做静默降级外的隐藏行为）。

### 4.5 检索结果的返回形态（上下文成本）

| 规则 | 依据 |
| --- | --- |
| 列表只回 `doc_slug / title / kind / version / updated_at / summary(<=120 字) / tags` | 与 coda-admin 的「列表只回摘要」一致（`scripts/mcp/coda_admin_mcp_server.py:198-208`） |
| 详情默认只回前 2000 字 + 「已截断」提示 | 与 `skill_get` 的截断纪律一致（`:715-716`） |
| 需要全文时显式传 `max_chars`（上限 20000）或 `offset` | 分页读取，避免一次调用灌满上下文 |
| 二进制只回**路径 + 大小 + mime**，不回 base64 | 大文件进上下文没有任何收益（`scripts/mcp/image_mcp_server.py:19-21` 同思路） |

### 4.6 MCP 工具面（新增，不改 coda-admin 的 22 个工具）

**建议新增一个同域内置服务器 `coda-content`**（`builtin_key="coda-content"`），而不是塞进 `coda-admin`：

| 理由 | 说明 |
| --- | --- |
| 权限信封不同 | `coda-admin` 是「平台管理面」（默认 `ro`）；内容写入是**日常动作**，默认应 `rw` 但只作用于自己的项目 |
| 工具数量 | 22 个已经不小；再加 8 个会让模型选错工具的概率上升 |
| 可停用 | 不想让 AI 写内容的人直接停用这一个服务器，不必关掉整个管理面 |
| 复用同一套纪律 | stdio + PAT + `ro/rw` + `confirm` + 摘要返回 + `isError` 文本：全部照搬 `coda-admin`（`:180-195`、`:942-948`） |

工具清单（8 个）：

| 工具 | 变写 | 参数 | 返回 |
| --- | --- | --- | --- |
| `content_put` | ✅ | `project`、`title`、`kind`、`content`/`content_base64`/`source_path`、`doc_slug?`、`summary?`、`tags?`、`supersedes_version?`、`idempotency_key?`、`confirm` | `doc_id`、`version_no`、`content_sha256`、`deduped`（是否命中已有对象） |
| `content_get` | — | `doc_id` 或 `(project, doc_slug)`、`version?`、`max_chars?`、`offset?` | 元数据 + 正文（截断提示）或二进制路径 |

| `content_search` | — | `q`、`project?`、`limit?` | 命中摘要 + 高亮片段（≤ 200 字） |
| `content_link` | ✅ | `doc_id`、`project`、`role?`、`confirm` | 已登记引用（不复制字节） |
| `content_versions` | — | `doc_id` | 版本账本（版号 / 来源 / 操作者 / 时间 / 大小） |
| `content_restore` | ✅ | `doc_id`、`version_no`、`confirm` | 新版本号（`source=rollback`） |
| `content_delete` | ✅ | `doc_id`、`confirm` | 软删文档并摘引用；**不**立即删字节（GC 宽限期） |

错误约定（与 `coda-admin` 一致，全部以 `isError` 文本回给模型）：

| 情况 | 文案要点 |
| --- | --- |

| 只读模式 | 「这个服务器配置为只读，拒绝写操作；到 MCP 页把 `CODA_MODE` 改为 rw」（照搬 `:180-186`） |
| 未确认 | 「请在参数里显式传 confirm=true」（照搬 `:189-195`） |

## 5. 与现有用法的兼容与迁移

### 5.1 兼容原则

| 现有用法 | 兼容做法 |
| --- | --- |
| 附件（`attachments/…`，`backend/app/attachments.py:69-82`） | **不改**。附件仍是「消息的一部分」，只是额外登记一条 `role=reference` 的内容引用（可关） |
| 生图 / 抓图（`generated-images/…`） | **不改**。产物是对话的展示对象；需要复用时用 `content_put(source_path=…)` 收进库 |
| 技能库（`skill-libraries` + `.mounts.json`） | **不动**。技能有自己的版本方案（`skills-versioning-plan.md`），两套库不要互相吞并 |
| 工作目录（`workspaces/<对话 id>`） | **保留**。它是 AI 的操作面；内容库不接管它，只做对账扫描 |
| coda-admin（22 工具） | **不改**。新工具放独立服务器，`coda-admin` 的契约零变化 |
| 只读文件出口 | 复用同样的路径校验思路（`attachments.resolve_workspace_file:84`），不新写一套穿越防护 |

### 5.2 分阶段实施（每阶段都可独立上线、独立回滚）

| 阶段 | 内容 | 是否改现有行为 | 回滚点 |
| --- | --- | --- | --- |
| **P0 地基** | 新增表 + `content-store` 目录 + `content_put/get/list` 三个工具（只服务新数据） | 否（老路径完全不变） | 删目录 + 删表；老功能零影响 |
| **P1 检索** | `content_search` + `content_tags` + FTS5（含 trigram / LIKE 双路） | 否 | 关 `CODA_CONTENT_SEARCH` 开关，退回 LIKE |
| **P2 对账** | 运行收尾扫描工作目录新增文件，登记为 `source=scan`（**只登记，不移动字节**，原路径记 `legacy_path`） | 微弱（多一次扫描） | 关 `CODA_CONTENT_SCAN` 开关即停 |
| **P3 迁移** | `scripts/migrate_content_store.py`（手工、可 dry-run）：按哈希去重后把**确认过**的文件收进库，项目侧生成 `index.jsonl` | 是（可选、按项目逐个迁） | 每项目保留 `legacy_path`，删库即回到 P2 状态 |
| **P4 收口** | 新数据只走内容库；工作目录里的历史文件转为只读引用 | 是 | 保留 P3 的 `legacy_path` 与备份，可整体退回 |

> 每个阶段的共同纪律：**数据只增不改**。内容库目录独立于老路径，任何阶段删掉它都不会影响老功能。

### 5.3 旧数据如何适配

| 旧数据形态 | 判定 | 处理 |
| --- | --- | --- |
| 工作目录里的散文件（无元数据） | 扫描时按后缀 + 魔数分类 | 登记 `kind=other`、`title=文件名`、`source=scan`；**不**自动建版本历史（只留首次快照） |
| 同名不同内容的老文件 | 哈希不同 | 各自入库（内容寻址天然不覆盖），`doc_slug` 冲突时追加 `-2`、`-3` 并记 `note=同名冲突` |
| 同名同内容（重复副本） | 哈希相同 | 只留一份对象，其余变成同一文档的多个 `legacy_path`（记录在 `meta`） |
| `conversations.workspace_dir` 为空的历史对话 | 按 `settings.workspaces_root / conversation.id` 现算（`backend/app/runtime/service.py:141` 的规则） | 扫描时用同一规则解析；目录不存在则跳过 |
| 超限文件（> 32 MB） | 大小超阈值 | 只登记路径 + 哈希（`role=reference`），正文不入库，检索结果标注「外置」 |
| 二进制 / 图片 | mime 非文本 | 入库但不进 FTS；只按项目/标签/时间检索 |
| 带敏感信息的文件 | 迁移时人工标记或按目录规则 | `sensitive=true`，不进全文索引 |

### 5.4 回滚手册（逐阶段）

| 从哪退回 | 操作 | 数据影响 |
| --- | --- | --- |
| P4 → P3 | 打开 `CODA_CONTENT_WRITE=legacy`，新数据回工作目录 | 内容库仍在，只读 |
| P3 → P2 | 停止迁移脚本；已迁项目保留 `index.jsonl` 与 `legacy_path` | 老路径仍完整可读 |
| P2 → P1 | 关 `CODA_CONTENT_SCAN` | 不再自动登记；已有登记保留 |
| P1 → P0 | 关 `CODA_CONTENT_SEARCH` | 退化为按项目/标签/时间 |
| P0 → 现状 | 删 `content-store/` + 删四张表 | 老功能零影响（P0 只服务新数据） |

**迁移前必做**：`cp -a backend/data backend/data.bak-$(date +%Y%m%d)`（因为 `backend/data/` 被 git 忽略，
`git` 不提供任何恢复能力，`.gitignore:13`）。

### 5.5 验收标准（可执行的检查项）

- [ ] 同一 5 MB 文件写入 3 个不同项目后，`objects/` 下只增加 1 个文件，磁盘增量 ≈ 5 MB（不是 15 MB）；
- [ ] `SELECT hash, count(*) FROM content_objects GROUP BY hash HAVING count(*)>1` 恒为空；
- [ ] 删除其中一个项目的引用，另一个项目仍可读出完整内容（O4）；
- [ ] 同一 `idempotency_key` 重试 3 次，`document_versions` 只多 1 行；
- [ ] 改写内容后 `doc_id` 不变、`version_no` +1、旧版本可 `content_get(version=n)` 读回；
- [ ] 5 MB 文件写入中断（kill -9）后，`objects/` 无半成品文件，`tmp/` 残留由 GC 清理；
- [ ] 中文 3 字以上查询能命中；2 字查询走 LIKE 并返回结果（不空手而归）；
- [ ] 关闭全部开关后，原有对话 / 附件 / 生图 / 技能链路行为零变化（回归测试全绿）。

## 6. 整体方案对比与推荐

### 6.1 三个整体方案

- **方案 A（推荐）：中央内容库 + 项目索引** —— 本文 §2/§3 的设计。新表 + 新目录 + 新 MCP 服务器，
  项目侧只放引用与元数据。
- **方案 B：项目目录自持（项目内嵌 + 平台编目）** —— 把 `workspace` 当项目，内容就是文件，
  平台只维护一张「项目 → 文件路径」的目录表，外加轻量哈希做去重提示。
- **方案 C：全量复制 + 同步** —— 每个项目各存一份实体，平台负责把更新推给所有副本。

### 6.2 对比表

| 维度 | 方案 A：中央库 + 索引 | 方案 B：项目自持 + 编目 | 方案 C：全量复制 + 同步 |
| --- | --- | --- | --- |
| **优点** | 内容真正一份（O1）；版本 / 审计 / 检索天然可行；跨项目复用零成本；删除语义清晰（引用计数） | 改造最小，几乎沿用现有「文件就在工作目录」；AI 零学习成本；单项目内体验最好 | 每个项目都自带完整内容，脱离平台也能用；单项目读取最快（无 join） |
| **缺点** | 需要新表 + 新目录 + 新工具；`documents`/`content_objects` 两套身份需要理解成本；项目概念要先定 | 跨项目同一内容仍是多份；无版本、无审计；AI 直接改磁盘平台看不见；全文检索要全盘扫 | 存储 N 倍膨胀；一致性靠同步逻辑（最难写对）；「哪份是准的」长期无人能答；删除/权限语义混乱 |
| **改造成本** | 中（后端 4 张表 + 8 个工具 + 1 个迁移脚本；前端一个内容页 <= 3 天） | 低（1 张表 + 列表接口，约 1 天） | 高（同步引擎 + 冲突解决 + 重试队列，> 1 周且长期维护） |
| **风险** | ① 项目边界未定（产品问题）；② AI 绕过工具直接写磁盘；③ 硬链接视图被就地改写污染对象；④ FTS 中文分词 | ① 需求「只存一份」根本满足不了；② 治理能力永远补不上（要回头做 A）；③ 大量重复占盘 | ① 同步发散导致内容不一致；② 冲突解决复杂度无上限；③ 回滚困难（要回滚 N 份） |
| **适用场景** | 多智能体 / 多项目共用同一份知识，要求版本与审计（**Coda 的形态**） | 单人单项目、纯本地、不关心历史 | 完全离线、彼此隔离的多个部署，且内容变更极少 |

### 6.3 明确推荐：**方案 A**

理由（按重要性排序）：

1. **它才满足需求本身**。工单的归属模型要求「内容只存一份、项目侧只放索引/引用与元数据」——
   B 与 C 从定义上就做不到，只有 A 能同时满足「一份字节」与「N 个项目可见」。
2. **它复用了仓库已经验证过的形态**。`skill-libraries/<owner>/<slug>` + `.mounts.json`
   （`backend/app/runtime/skills.py:99-118`）就是「单实体 + 引用登记」；`docs/计划任务/skills-versioning-plan.md:227-240`
   已经论证过 `blobs/<sha256>` 内容寻址。A 不是新发明，是把这两条既有纪律推广到「任意内容」，
   团队已有的心智模型可以直接迁移。
3. **它把治理能力做在正确的层**。版本、审计、去重、检索都在平台侧，AI 只能通过 MCP 工具写，
   平台第一次「看得见」内容变更 —— 这正是 `docs/计划任务/skills-versioning-plan.md:106-120` 里
   「AI 改文件平台毫不知情」的解法。
4. **成本可控且可分阶段**。P0 只服务新数据、零风险；老功能一路不动（§5.2）；最坏情况删目录删表即可回到现状。

### 6.4 为什么不选其余

- **不选 B**：它的低成本是假象 —— 需求里的「去重 / 版本 / 检索」三项它一项都给不了，
  真做起来会演化成「在项目目录里维护一个半吊子索引」，最终还是回到 A，等于交两次学费。
  B 唯一值得保留的部分是「工作目录仍是 AI 的操作面」，这一点 A 已经原样保留了（§2.6）。
- **不选 C**：N 倍存储只是表面代价，真正的问题是一致性 —— 同步逻辑是所有方案里最容易写错、
  最难测、最难回滚的部分。为了一个「内容只存一份」的需求去引入「必须同步 N 份」的机制，方向是反的。

### 6.5 成本估算（方案 A，按阶段）

| 阶段 | 主要工作 | 预估 |
| --- | --- | --- |
| P0 | 4 张表 + 目录布局 + 3 个工具 + 单测（写/读/去重/幂等/中断） | 2–3 天 |
| P1 | 标签 + FTS5（trigram/LIKE 双路）+ 检索工具 | 1–2 天 |
| P2 | 运行收尾对账扫描（只登记） | 1 天 |
| P3 | 迁移脚本（dry-run / 逐项目 / 备份校验） | 1–2 天 |
| P4 | 收口 + 前端内容页（列表 / 详情 / 版本） | 2–3 天 |

（PAT + ro/rw + confirm + 摘要返回 + `isError` 文本）推导而来，未假设任何不存在的代码。

平台也还没有「内容」这个实体。要做统一存储，正确的地基是**按 owner 隔离的内容寻址对象库**
（一份字节）+ **逻辑文档与版本账本**（SQLite）+ **项目侧只有引用与元数据**（`project_contents` / `index.jsonl`）。
