# 统一凭据池与多账号轮询层方案

> 状态：**方案，尚未开工**。
> 适用对象：需要把「多个账号 / 多把密钥」聚合成一个池、让智能体自动轮询与失败转移的使用者；以及要落地这套机制的工程师。
>
> **已定方向：账号槽位池挂在内核上（按 `type_id`），API Key 池仍挂在网关上。**
> 理由：OAuth 登录态天然属于内核（同一台机器上 CodeBuddy 只有一份登录态）；而 API Key 属于模型端点，项目铁律要求「网关是 API Key 的唯一来源」。两条链路各自挂在最自然的位置，不互相污染。
>
> 事实基线：Coda `main` 分支当前工作区。**代码是唯一事实来源**；本文与代码冲突时以代码为准。
>
> 相关文档：`AGENTS.md`（铁律与分层）、`docs/架构/architecture.md`（运行时序）、`docs/功能文档/usage-gateway.md`（记录网关与账本）、`docs/功能文档/codebuddy-cli.md`、`docs/功能文档/doubao-cli.md`。

## 0. 一句话结论

新增一个**框架层统一池**（`CredentialBroker`）+ **适配器层凭据挂载接口**（`AccountProvider`）：

- 框架统一负责：选谁、什么策略、谁冷却了、谁被占用、这次用了多少；
- 适配器负责：这个内核的凭据存在哪、怎么物化进本次运行、结束后怎么回写；
- **账号槽位池挂内核**：按 `type_id` 存一份池配置与成员，同一内核的所有智能体共享；
- **API Key 池挂网关**：仍由 `Gateway` 承载，符合「网关是 API Key 唯一来源」的铁律；
- **OAuth / 登录态型内核**走运行级账号槽位轮询；
- **API Key 型内核**走记录网关的请求级 Key 池。

落地顺序：**CodeBuddy（已验证）→ Codex（最简单）→ Claude Code / Antigravity（中等）→ 豆包（最难）**。

## 1. 问题、目标与非目标

### 1.1 现状

| 层 | 现状 | 代码位置 |
| --- | --- | --- |
| 网关 | 一个网关 = 一个端点 + 一把 `api_key_encrypted` | `backend/app/models.py:188` `Gateway` |
| 运行绑定 | 一次运行只绑定一个地址 + 一把密钥 | `backend/app/runtime/gateway.py:37` `bind_gateway()` |
| 记录网关 | 一个 `ProxyTarget` 只持有一把上游密钥 | `backend/app/runtime/recording_gateway.py:74` `ProxyTarget` |
| 内核账号 | CodeBuddy 有槽位，但 `activate_account()` 是**写回全局登录态** | `backend/app/agents/builtin/codebuddy_accounts.py:287` |
| 并发 | 切换锁只串行化「切换动作」，不保证运行期间仍是目标账号 | `backend/app/runtime/service.py:43-47` |
| 后台任务 | 起标题等后台任务为避免串号，直接跳过切号 | `backend/app/runtime/titles.py:266-271` |

### 1.2 用户痛点

- CodeBuddy 有很多账号，每个账号额度很少；
- 现在只能手动切号，切完还会影响正在跑的对话；
- 智能体绑定 CodeBuddy 后，无法自动把请求分摊到多个账号；
- 某个账号额度用完，只能人工发现、人工换号；
- 后续还想让 Claude Code、Codex、豆包都具备类似能力。

### 1.3 目标

1. **内核级账号池**：一个内核（按 `type_id`）挂多个账号槽位，同一内核的所有智能体共享；API Key 池仍按网关隔离。
2. **自动轮询**：每次运行自动选一个健康的成员，不需要用户手动切。
3. **多种策略**：轮询、顺序、最少使用、加权、主备、对话粘性。
4. **健康与冷却**：429 / 额度错误 / 鉴权失败自动标记，冷却期内跳过。
5. **失败转移**：首响应前失败可换下一个；已产生副作用则不重跑。
6. **用量归属**：账本能按账号 / 密钥维度汇总。
7. **跨内核**：同一套策略与 UI，适配器只实现自己的凭据挂载。
8. **并发安全**：不同运行可以用不同账号同时跑，不互相踩全局登录态。

### 1.4 非目标

- ❌ **物理合并额度**：厂商按账号计费，平台只能分散请求 + 汇总展示，不能把 A 的余额转给 B。
- ❌ **OAuth 请求级轮换**：不在记录网关里逐请求替换 OAuth access token；刷新链、token 轮换、设备身份都不可控。
- ❌ **主动查询厂商余额**：CodeBuddy 本地状态接口目前只返回 `authenticated + account`，没有额度字段；先做被动识别。
- ❌ **绕过厂商条款**：多账号轮换可能触发风控；只用于使用者有权使用的账号，并提供冷却、告警与审计。

## 2. 事实基线（代码证据）

### 2.1 网关与密钥

- `Gateway` 只有一把 `api_key_encrypted`，没有池的概念（`backend/app/models.py:188`）。
- `bind_gateway()` 解析一次运行只返回一个 `url/api_key/auth_style`（`backend/app/runtime/gateway.py:37`）。
- 记录网关的 `ProxyTarget` 也只持有一把 `api_key`（`backend/app/runtime/recording_gateway.py:74`）。
- 自定义网关的密钥只经 `app/security.py` 解密，禁止出现在日志、事件与响应里（`AGENTS.md` §7）。

### 2.2 内核账号能力

`AgentDefinition` 目前只有：

- `auth_status()`：探测登录态（可选）；
- `activate_account()` / `remove_account()`：多账号槽位（可选）；
- `supports_accounts()`：是否覆盖了 `activate_account`（`backend/app/agents/base.py:471`）。

这套接口只支持「切换到某个账号」，不支持「每次运行独立选号 / 物化 / 回写」。

### 2.3 各内核登录态的真实位置

| 内核 | 登录态存储 | 现有能力 | 关键约束 |
| --- | --- | --- | --- |
| **CodeBuddy** | `$HOME/.../CodeBuddyExtension/Data/Public/auth/*.info` | 有槽位，但只能手动切 | 登录态跟真实 `HOME` 走，不受 `CODEBUDDY_CONFIG_DIR` 影响 |
| **Codex** | `$CODEX_HOME/auth.json`（默认 `~/.codex`） | 无多账号 | 配置与登录态都在 `CODEX_HOME`，隔离最干净 |
| **Claude Code** | `$CLAUDE_CONFIG_DIR` + `.claude.json`（默认 `~/.claude`）；macOS 可能在 Keychain | 无多账号 | Keychain 是跨平台差异点 |
| **豆包** | 数据目录（`XDG_DATA_HOME` / `Application Support`）+ `mssdk` 设备身份 | 有登录，无多账号 | 登录态与设备身份必须一起搬；Windows 原生程序认 `USERPROFILE` |
| **Antigravity** | `~/.gemini/antigravity-cli` 下的 JSON 凭据 | 有登录，无多账号 | 凭据文件名不固定，按内容扫描 |
| **DeepSeek / Hermes / OpenAI Harness / custom-cli** | API Key 环境变量 | 不需要账号槽位 | 走网关 Key 池即可 |

对应代码：

- CodeBuddy：`backend/app/agents/builtin/codebuddy_accounts.py`、`codebuddy_cli.py:116`；
- Codex：`backend/app/agents/builtin/codex.py:60` `_CARRY_FILES`、`:83` `codex_home()`；
- Claude Code：`backend/app/agents/builtin/claude_code.py:134` `config_dir()`、`:140` `user_config_file()`；
- 豆包：`backend/app/agents/builtin/doubao_cli.py` 的 `_link_macos_data()` / `_link_windows_data()` / `XDG_DATA_HOME` 处理；
- Antigravity：`backend/app/agents/builtin/antigravity_cli.py:59` `_APP_DIRNAME`、`read_credentials()`。

### 2.4 可行性实测（详见附录）

已用**同一台机器上的一个已保存账号**验证：

1. 把 session 复制到临时 `HOME` 的对应 auth 路径；
2. 用 `HOME=<临时目录>` 启动 `codebuddy --serve`；
3. `/api/v1/auth/account/status` 返回目标账号已认证；
4. 用免费模型 `hy4flash-free` 完整跑一次 `codebuddy -p`，退出码 0。

结论：**per-run HOME 隔离成立，CodeBuddy 运行级轮询可行。**

## 3. 核心设计

### 3.1 分层图

```text
AgentProfile
   ├─ type_id ──► Kernel（内核级账号池，按 type_id 共享）
   │                 └─ official 链路 ──► 选账号 ──► 物化运行环境 ──► 子进程
   │
   └─ gateway_id ──► Gateway（自定义网关）
                       └─ API Key 池 ──► 记录网关（请求级轮询 / 429 重试）──► 上游
```

**判断顺序**：

1. 智能体走**自定义网关** → 走网关的 API Key 池（如果有），内核账号池不参与；
2. 智能体走**官方链路**（`gateway_id` 为空或 `kind=official`）→ 看它绑定的内核有没有开启账号池；
3. 内核账号池开启 → 选账号槽位；未开启 → 现状（跟随内核当前登录态）。

框架层只做「池」；适配器层只做「凭据怎么放」。

### 3.2 两种后端

| 后端 | 挂载位置 | 适用 | 注入点 | 轮询粒度 | 回写 |
| --- | --- | --- | --- | --- | --- |
| **账号槽位池** | **内核**（`type_id`） | OAuth / 登录态型内核 | `HOME` / `CODEX_HOME` / `CLAUDE_CONFIG_DIR` / 数据目录 | **运行级** | 必须回写刷新后的凭据 |
| **API Key 池** | **网关**（`gateway_id`） | 自定义网关、API Key 型内核 | `Invocation.env` 或 `ProxyTarget` | **请求级**（经记录网关） | 不需要 |

两种后端共享：选号策略、健康状态、冷却、租约、用量归属。区别只在「挂在哪」和「怎么注入」。

> 为什么账号池不挂网关：OAuth 登录态是**机器级 / 内核级**资产，同一台机器上 CodeBuddy 只有一份登录态；如果挂网关，用户建两个官方网关就会得到两套互不相干的池，反而不好用。挂内核则「登录一次、所有 CodeBuddy 智能体共享」。

### 3.3 一次运行的生命周期

```text
1. 载入 AgentProfile / Gateway / AgentDefinition
2. 判断链路：
   - 自定义网关 → 不碰内核账号池；有 API Key 池就走网关
   - 官方链路 → 看 definition 的内核账号池
3. 解析「固定覆盖」还是「池」
   - profile.account_id 有值 → 固定账号槽位（兼容旧行为）
   - 内核开启了账号池 → 选一个健康成员
   - 都没有 → 现状（跟随内核当前登录态）
4. 选成员（策略 + 健康 + 租约）
5. 构建 AgentContext
6. 物化技能 / MCP 隔离目录（ctx.home_dir）
7. 适配器 materialize()：把成员凭据放进本次运行，返回 env 覆盖
8. 启动子进程 / 发起请求
9. 采集 usage、错误事件
10. finally：capture() 回写刷新后的凭据；释放租约；清理运行目录
11. 失败时：按分类标记冷却 / 失效，必要时换下一个成员重试
```

### 3.4 注入策略（由适配器决定）

| 策略 | 典型内核 | 做法 |
| --- | --- | --- |
| `env` | API Key 型 | 返回 `{OPENAI_API_KEY: ...}` / `{ANTHROPIC_AUTH_TOKEN: ...}` |
| `config_dir` | Codex / Claude Code | 返回 `{CODEX_HOME: ...}` / `{CLAUDE_CONFIG_DIR: ...}`，把 `auth.json` / 凭据文件放进目录 |
| `home` | CodeBuddy / Antigravity | 返回 `{HOME: ..., USERPROFILE: ...}`，用符号链接农场隔离 auth 子树 |
| `data_dir` | 豆包 | 返回 `{XDG_DATA_HOME: ...}`，macOS/Windows 由适配器做目录链接 |
| `proxy_key` | API Key 池 | 注册多个 Key 到 `ProxyTarget`，由记录网关逐请求选 |

**框架不硬编码任何具体路径。** 这符合 `AGENTS.md` §4「框架层不得硬编码内核 id / 包管理器 / 具体路径」的约定。

### 3.5 回写策略

| 凭据类型 | 是否需要回写 | 说明 |
| --- | --- | --- |
| API Key | ❌ | 不会变 |
| Codex `auth.json` | ✅ | 内核可能刷新 token |
| CodeBuddy `.info` | ✅ | 刷新后必须写回槽位，否则可能丢 refresh token |
| Claude Code 凭据 | ✅ | 取决于存储位置；Keychain 需单独处理 |
| 豆包数据目录 | ✅ | 设备身份 / token 可能更新 |
| Antigravity JSON | ✅ | OAuth refresh 可能更新 |

**回写是硬要求**，不是优化项：OAuth refresh token 可能轮换，不回写会把槽位跑废。

## 4. 数据模型

### 4.1 新表 `kernel_credential_pools`

内核池按 `type_id` 唯一，一台机器上一个内核只有一份池配置；不随网关 / 用户创建多份。

```text
kernel_credential_pools
  type_id                 VARCHAR(64) PK   # codebuddy / codex / doubao / ...
  enabled                 BOOLEAN          # 是否启用；关闭时行为与现状一致
  strategy                VARCHAR(32)      # round_robin | sequential | least_recently_used | weighted | failover
  sticky                  BOOLEAN          # 同一对话是否固定成员
  max_retries             INTEGER          # 首响应前失败最多换几次
  cooldown_seconds        INTEGER          # 默认冷却基数
  max_concurrent_per_member INTEGER        # 同一成员最多几个并发运行（OAuth 建议 1）
  created_at / updated_at DATETIME
  updated_by              VARCHAR(64)      # 最后修改的管理员 id，用于审计
```

> 内核本身是静态注册的（`AgentDefinition`），没有 `kernels` 表；因此池配置直接用 `type_id` 作为主键，不依赖外键。启动时若池行不存在，按默认值懒创建。

### 4.2 新表 `kernel_credential_members`

```text
kernel_credential_members
  id                       TEXT PK
  type_id                  VARCHAR(64)   # 所属内核，索引
  slot_ref                 VARCHAR(64)   # 适配器槽位 id（CodeBuddy 的槽位、Codex 的 auth 槽位...）
  label                    VARCHAR(120)  # 展示名（昵称 / 邮箱 / 企业）
  priority                 INTEGER       # failover / sequential 用，越小越优先
  weight                   INTEGER       # weighted 用，默认 1
  enabled                  BOOLEAN
  state                    VARCHAR(16)   # ready | cooling | disabled
  cooldown_until           DATETIME
  last_used_at             DATETIME
  lease_owner              VARCHAR(64)   # 当前占用的 run id
  lease_until              DATETIME
  success_count            INTEGER
  failure_count            INTEGER
  last_error               TEXT
  created_at / updated_at  DATETIME
```

约束与索引：

- `UNIQUE(type_id, slot_ref)`：同一账号不会重复入池；
- `(type_id, enabled, state)`；
- `(type_id, cooldown_until)`；
- `(type_id, last_used_at)`。

**安全约定**：

- 这张表**不存凭据 blob**，只存 `slot_ref`；实际 session / auth 文件仍在适配器的槽位目录（0600），由 `AccountProvider` 读取；
- `last_error` 必须是脱敏后的短文本，禁止写入 token / session；
- 如果未来要支持「内核原生 API Key」（不是网关 Key），再单独加 `secret_encrypted` 列，不要复用网关密钥。

### 4.3 归属字段

| 表 | 新字段 | 用途 |
| --- | --- | --- |
| `conversations` | `credential_member_id VARCHAR(64)` | 粘性：同一对话固定成员 |
| `usage_records` | `credential_member_id VARCHAR(64)` | 账本按账号维度汇总 |
| `agent_profiles` | 沿用 `account_id` | 固定账号槽位覆盖；有值时优先于池 |

`usage_records.credential_member_id` 是后加列，登记到 `ADDITIVE_COLUMNS["usage_records"]`；`conversations.credential_member_id` 同理。

> API Key 池仍挂在 `Gateway` 上（Phase 5 再扩），不放进内核池表。这样「网关是 API Key 唯一来源」的铁律不被破坏。

### 4.4 为什么池挂在 `type_id` 而不是 `gateway_id`

1. **登录态是内核级资产**：同一台机器上 CodeBuddy 只有一份登录态，账号槽位天然属于内核；
2. **用户心智是「这个内核有哪些账号」**：不是「这个网关有哪些账号」；
3. **避免重复池**：同一内核可能被多个智能体、多个官方链路口径使用；挂网关会得到多份互不相干的池；
4. **权限一致**：账号槽位是机器级 / 管理员资产（现有 `api/runtimes.py` 只对管理员暴露账号清单），挂内核后权限模型不用改；
5. **API Key 仍走网关**：它属于模型端点，不属于内核，二者不要混。

如果未来需要「一个内核的池按用户隔离」，再加 `owner_id` 或 `scope` 列；v1 先按机器级唯一。

## 5. 适配器接口

### 5.1 数据结构

放在 `backend/app/agents/base.py`：

```python
@dataclass(slots=True)
class AccountMount:
    """一次运行要注入的账号环境；由适配器决定落点。"""
    env: dict[str, str] = field(default_factory=dict)
    #: 要写进运行目录 / 隔离目录的文件（相对路径 -> 内容）
    files: dict[str, bytes] = field(default_factory=dict)
    #: 面向用户的说明 / 告警（不带凭据）
    notes: list[str] = field(default_factory=list)


class AccountProvider(Protocol):
    def list_accounts(self) -> list[RuntimeAccount]: ...

    def snapshot_current(self) -> str | None:
        """把内核当前登录态存成槽位；不支持返回 None。"""

    def materialize(
        self, account_id: str, *, run_dir: Path, home_dir: Path | None
    ) -> AccountMount:
        """把账号凭据放进本次运行；返回 env 覆盖。"""

    def capture(
        self, account_id: str, *, run_dir: Path, home_dir: Path | None
    ) -> None:
        """运行结束把刷新后的凭据写回槽位；失败只告警，不抛给用户。"""

    def classify_failure(self, text: str, status: int | None) -> str | None:
        """返回 'quota' / 'auth' / None。"""
```

### 5.2 AgentDefinition 增补

```python
def account_provider(self) -> AccountProvider | None:
    """返回本内核的账号挂载实现；None 表示不支持账号池。"""
    return None

def supports_account_pool(self) -> bool:
    return self.account_provider() is not None
```

兼容约定：

- `supports_accounts()` / `activate_account()` **保留**，用于手动切号与旧行为；
- 池模式**不调用** `activate_account()`，避免改全局登录态；
- 适配器可以同时支持「手动切号」与「池模式」，由 `kernel_credential_pools.enabled` 决定走哪条。

### 5.3 框架 `CredentialBroker`

新增 `backend/app/runtime/credential_broker.py`：

```python
@dataclass(slots=True)
class ResolvedCredential:
    member_id: str
    kind: str                 # v1 只有 account_slot
    type_id: str              # 所属内核
    label: str
    env: dict[str, str] = field(default_factory=dict)
    run_dir: Path | None = None
    provider: AccountProvider | None = None

class CredentialBroker:
    async def resolve(
        self, session, definition, gateway, profile, conversation, run_id
    ) -> ResolvedCredential | None:
        """官方链路 + 内核池开启时才返回；自定义网关返回 None，交给网关 Key 池。"""
        ...

    async def release(self, member_id: str, run_id: str) -> None: ...

    async def report_failure(
        self, member_id: str, *, status: int | None, text: str
    ) -> None: ...

    async def report_success(self, member_id: str) -> None: ...
```

职责：

- 选成员（策略 / 健康 / 粘性 / 固定覆盖）；
- 原子租约（OAuth 成员默认串行）；
- 物化 / 回写（调适配器）；
- 失败分类与冷却；
- 用量归属提示（把 `member_id` 交给运行层写账本）。

**作用域判断**：

```python
if gateway is not None and gateway.kind == "custom":
    return None                     # 自定义网关不碰内核账号池
if not definition.supports_account_pool():
    return None                     # 内核没有账号槽位
pool = await load_kernel_pool(session, definition.type_id)
if not pool.enabled:
    return None                     # 未开启池：走现状 / 手动切号
```

### 5.4 选号伪代码

```python
async def select(session, definition, gateway, conversation, run_id):
    if gateway is not None and gateway.kind == "custom":
        return None
    if not definition.supports_account_pool():
        return None

    pool = await load_kernel_pool(session, definition.type_id)
    if not pool or not pool.enabled:
        return None

    now = utcnow()
    if pool.strategy == "failover" or pool.strategy == "sequential":
        order = "priority ASC, last_used_at ASC"
    elif pool.strategy == "round_robin":
        order = "last_used_at ASC"          # 最久未用优先
    elif pool.strategy == "weighted":
        order = None                         # 按 weight 随机
    else:
        order = "last_used_at ASC NULLS FIRST"

    candidates = await load_healthy_members(definition.type_id, now)
    if pool.sticky and conversation.credential_member_id:
        pinned = next((m for m in candidates if m.id == conversation.credential_member_id), None)
        if pinned:
            candidates = [pinned]

    member = choose(candidates, strategy=pool.strategy, order=order)
    if member is None:
        raise NoAvailableCredential(...)

    acquired = await lease(member.id, run_id, now)
    if not acquired:
        return await select(session, definition, gateway, conversation, run_id)

    await touch_last_used(member.id, now)
    return member
```

> 单进程（当前桌面版是单个 uvicorn）用 `asyncio.Lock` + 事务即可；未来多 worker 时改成数据库原子更新 / `BEGIN IMMEDIATE`，不改变接口。

## 6. 运行接线

### 6.1 `prepare_run` 的顺序调整

当前 `backend/app/runtime/service.py` 在 `prepare_run` 里先调 `activate_selected_account()`（约 `:590`），再构建上下文、物化技能与 MCP（约 `:652`）。池模式需要改成：

```text
载入 profile / gateway / definition
  → broker.resolve(definition, gateway, profile, conversation, run_id)
       ├─ 自定义网关 → 返回 None（内核账号池不参与）
       ├─ 内核池未开启 → 返回 None
       ├─ profile.account_id 有值 → 固定槽位
       └─ 否则按内核池策略选一个成员
  → build_context()              # 把 member_id / type_id 放进 ctx
  → prepare_skill_home()         # 得到 ctx.home_dir
  → provider.materialize()       # 用 run_dir + ctx.home_dir 物化凭据
  → 合并 env 到 ctx
  → 启动运行
  → finally: provider.capture() + broker.release()
```

非池模式（内核池 `enabled=false` 或走自定义网关）保持现有 `activate_selected_account()` / 单 Key 行为，零回归。

### 6.2 环境变量合并顺序

`backend/app/runtime/runner.py:250` 目前是：

```python
env = {**os.environ, **proxy_env_for_subprocess(), **ctx.credentials, **invocation.env}
```

池模式新增 `ctx.credential_env`，并让它**最后合并**，保证账号隔离变量不被用户环境覆盖：

```python
env = {
    **os.environ,
    **proxy_env_for_subprocess(),
    **ctx.credentials,
    **invocation.env,
    **ctx.credential_env,          # 新增：HOME / CODEX_HOME / CLAUDE_CONFIG_DIR ...
}
```

同时修正一个已知副作用：

- `runner.py:253` 用合并后的 `HOME` 拼 `~/.local/bin`；如果池模式把 `HOME` 换成临时目录，会丢掉真实安装目录。
- 修法：在覆盖 `HOME` 之前，用**真实** `os.environ["HOME"]` 计算 `PATH`，或由适配器在 `credential_env` 里显式给出 `PATH`。
- Windows 同理：`USERPROFILE` 覆盖后，真实安装目录要显式保留。

### 6.3 与技能 / MCP 隔离的关系

- **CodeBuddy**：`CODEBUDDY_CONFIG_DIR` 是对话级隔离目录，和 `HOME` 是两套路径；账号池只需要替换 `HOME`，互不冲突。
- **Codex / Claude Code**：`CODEX_HOME` / `CLAUDE_CONFIG_DIR` 本身就是对话级隔离目录；账号物化是「把对应成员的 `auth.json` / 凭据文件覆盖进去」，不是再换一层 HOME。
- **豆包**：`HOME` 同时承担技能隔离和数据目录解析；账号池要额外把数据目录指向该成员的副本，适配器需要同时处理 `HOME`、`USERPROFILE`、`XDG_DATA_HOME` 和 `mssdk`。
- 具体落点由适配器的 `materialize()` 决定，框架只提供 `run_dir` 与 `home_dir`。

### 6.4 记录网关接线

`bind_recording()` 增加 `credential_member_id`，写进 `ProxyTarget`：

```python
target = registry.register(..., credential_member_id=member_id)
```

`_forward.py` 在响应状态 >= 400 时：

```python
if status_code in (401, 402, 403, 429):
    await broker.report_failure(
        target.credential_member_id, status=status_code, text=body_preview
    )
```

- `credential_member_id` 只对内核账号池有意义；自定义网关的 API Key 池继续用 `api_key_id`，两者不要混。
- 记录网关默认 `off` 时没有这一路；运行层仍可从 CLI 错误事件分类，保证兜底。

## 7. 各内核接入

### 7.1 总览

| 内核 | 池位置 / 类型 | 物化方式 | 难度 | 备注 |
| --- | --- | --- | --- | --- |
| CodeBuddy | **内核账号池**（account_slot） | per-run HOME + session 文件 | 已验证 | 先做；同内核所有智能体共享 |
| Codex | **内核账号池**（account_slot） | per-run `CODEX_HOME` + `auth.json` | 简单 | 第二个验证抽象 |
| Claude Code | **网关 Key 池优先**；内核账号池可选 | `CLAUDE_CONFIG_DIR` + `.claude.json`；macOS Keychain | 中等 | API Key 回退更稳 |
| Doubao | **内核账号池**（account_slot） | `XDG_DATA_HOME` / `Application Support` / `USERPROFILE` + `mssdk` | 较难 | 最后做 |
| Antigravity | **内核账号池**（account_slot） | `~/.gemini/antigravity-cli` + 登录快照 | 中等 | Keychain 需验证 |
| DeepSeek / Hermes / OpenAI Harness / custom-cli | **网关 Key 池**（api_key） | 记录网关 Key 池 | 简单 | 请求级 |

### 7.2 CodeBuddy

**已实现的部分**：

- `codebuddy_accounts.py` 已有槽位、索引、`snapshot_live()`、`activate()`；
- 登录助手 `codebuddy_login.py` 已能把登录快照存成槽位。

**需要补的**：

1. `materialize(account_id, run_dir, home_dir)`：
   - 建 per-run fake HOME（符号链接农场，保留真实 `~/.gitconfig`、`~/.ssh`、`~/.local/bin` 等）；
   - 把槽位 blob 复制到 `<fake_home>/.local/share/CodeBuddyExtension/Data/Public/auth/<auth_file>`；
   - 返回 `{"HOME": fake_home, "USERPROFILE": fake_home}`（Windows）。
2. `capture(account_id, run_dir, home_dir)`：
   - 运行结束把 `<fake_home>/.../auth/<auth_file>` 写回槽位；
   - 更新 `sha256` / `saved_at`；
   - 失败只告警，保留 fake home 供人工恢复（可选）。
3. 槽位索引增加 `auth_file` 字段：
   - 不同站点 / 产品的 session 文件名可能不同，不能只依赖全局 `live_file`。
4. 登录快照保持现有 `snapshot_live()`。

**默认并发**：每个账号 1 个运行（`kernel_credential_pools.max_concurrent_per_member=1`），避免并发刷新 token。

**池的作用域**：同一台机器上所有绑定 CodeBuddy 的智能体共享这个内核池；登录一次，所有 CodeBuddy 智能体都能轮询。

### 7.3 Codex

**现状**：

- `codex_home()` 认 `CODEX_HOME`，默认 `~/.codex`；
- `_CARRY_FILES = ("config.toml", "auth.json")`；
- `skill_mount()` 已经把这两个文件带进对话级隔离目录。

**接入方式**：

1. 槽位存一份 `auth.json`（以及必要的 `config.toml`），`slot_ref` 指向槽位；
2. `materialize()` 把槽位的 `auth.json` 写进 `ctx.home_dir`（或 per-run `CODEX_HOME`），返回 `{"CODEX_HOME": ...}`；
3. `capture()` 把运行后的 `auth.json` 回写槽位；
4. 不需要碰 `HOME`，这是比 CodeBuddy 更干净的隔离方式。

**注意**：

- 如果同一对话的 `CODEX_HOME` 被复用，要保证对话内运行串行（现有运行模型通常满足）；
- 多账号并发时，不同账号使用不同 `CODEX_HOME` 或不同成员租约。

### 7.4 Claude Code

**现状**：

- `config_dir()` / `user_config_file()` 认 `CLAUDE_CONFIG_DIR`；
- 目前没有 `auth_status()`，也没有多账号；
- 用户通常通过网关 `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_API_KEY` 使用。

**两条路**：

1. **API Key 路线（推荐先做）**：
   - 走网关 Key 池，请求级轮询；
   - 不碰登录态，跨平台一致；
   - 适合「多个 API Key、每个额度少」的场景。
2. **OAuth 路线**：
   - 每个账号一个 `CLAUDE_CONFIG_DIR`；
   - Linux 下复制凭据文件通常可行；
   - macOS 上 OAuth token 可能在 Keychain，需要 `security` 读写或使用官方 token 导出方式；
   - 需要新增登录快照 / 导入当前账号。

**建议**：Claude Code 的 v1 只做 API Key 池；OAuth 多账号等有明确需求再补。

### 7.5 豆包

**现状**：

- `login_argv` 与 `auth_status()` 已存在；
- 技能隔离已经处理了 `HOME`、`XDG_DATA_HOME`、macOS `Application Support`、Windows `USERPROFILE` / junction；
- `mssdk` 是设备身份，必须与登录态一起搬，否则报「安全存储不可用」。

**接入方式**：

1. 槽位保存该账号的 `doubao_cli` 数据目录 + `mssdk` 目录（按平台）；
2. `materialize()`：
   - Linux：`XDG_DATA_HOME` 指向槽位的数据根；
   - macOS：把槽位的 `Application Support/doubao_cli`、`mssdk` 链进 per-run HOME；
   - Windows：把槽位目录 junction 进 per-run `USERPROFILE` 对应的位置，并保留真实 `LOCALAPPDATA`；
3. `capture()`：回写可能更新的 token / 设备身份；
4. 先在 Linux/macOS 验证，Windows 单独做真机测试。

**风险**：设备身份与账号的绑定关系、Windows Known Folder API 行为、内核更新后的数据目录变化。

### 7.6 Antigravity

**现状**：

- 凭据在 `~/.gemini/antigravity-cli` 下，按内容扫描 `access_token` / `refresh_token`；
- 登录助手已支持 Google OAuth 授权码；
- 没有多账号槽位。

**接入方式**：

1. 登录后把整个 `antigravity-cli` 数据目录快照成槽位；
2. `materialize()` 用 per-run HOME 或数据目录隔离；
3. 验证 Google OAuth refresh 是否依赖系统 Keychain；如果依赖，参考 Claude Code 的 Keychain 处理或 API Key 回退。

### 7.7 API Key 型内核

DeepSeek Harness、Hermes、OpenAI Harness、custom-cli，以及用 API Key 的 Claude/Codex：

- 不需要 `AccountProvider`；
- 网关配置多把 Key；
- 记录网关逐请求选 Key；
- 401 / 429 自动重试下一把；
- 这是**请求级**轮询，比账号槽位更细。

实现要点：

- `ProxyTarget` 增加 `api_keys: list[str]` 与 `pick_key()`；
- `_forward.py` 在建立上游请求前选 Key；401/429 且响应体未开始流式输出时，换 Key 重试；
- 重试次数与退避可配置；
- 每把 Key 的健康状态放**网关侧**（Phase 5 新增 `gateway_api_keys` 表，或给 `Gateway` 加 Key 池配置）；不要塞进内核池表。

## 8. 策略、健康与失败转移

### 8.1 选号策略

| 策略 | 行为 | 适合 |
| --- | --- | --- |
| `round_robin` | 按 `last_used_at` 最久优先，轮流 | 账号额度差不多 |
| `sequential` | 按 `priority` 顺序，用完一个再用下一个 | 主账号优先、副账号兜底 |
| `least_recently_used` | 最久未用优先 | **默认推荐**，简单公平 |
| `weighted` | 按 `weight` 随机 | 账号额度大小不同 |
| `failover` | `priority` 最小优先，失败换下一个 | 主备 |
| `sticky`（叠加项） | 对话固定成员，失败才换 | **默认开启**，行为稳定 |

**推荐默认**（`kernel_credential_pools` 的字段）：

```text
strategy = least_recently_used
sticky = true
max_retries = 2
cooldown_seconds = 300
max_concurrent_per_member = 1
```

### 8.2 健康状态

| 状态 | 触发 | 行为 |
| --- | --- | --- |
| `ready` | 正常 | 可被选中 |
| `cooling` | 429 / 额度错误 / 临时限流 | 冷却期内跳过；到期自动回 `ready` |
| `disabled` | 401 / 403 / 凭据损坏 / 手动停用 | 不参与选号；需要重新登录或手动恢复 |

冷却退避建议：

```text
第 1 次：5 分钟
第 2 次：15 分钟
第 3 次：1 小时
第 4 次及以后：6 小时
```

> 如果厂商返回 `Retry-After`，优先用它；没有再用退避。

### 8.3 租约

- 仅 `account_slot` 需要默认串行（OAuth refresh token 轮换风险）；
- `lease_owner = run_id`，`lease_until = now + max(运行超时, 30 分钟) + 缓冲`；
- 运行结束 / 取消 / 异常都在 `finally` 释放；
- 进程崩溃时靠 `lease_until` 过期自动恢复；
- 启动时清理过期租约（可选）。

### 8.4 失败转移

| 阶段 | 处理 |
| --- | --- |
| 首响应前（无 assistant 输出、无工具调用） | 标记成员冷却，换下一个，最多 `kernel_credential_pools.max_retries` 次 |
| 已产生 assistant 输出 / 工具调用 | **不重跑**，把错误交给用户；标记成员 |
| 所有成员都不可用 | 明确提示「凭据池已耗尽，请登录新账号或等待冷却」 |
| 鉴权失败 | 标记 `disabled`，提示重新登录；不自动重试同成员 |

> 重跑只在「确定没有副作用」时发生；这是安全底线。

## 9. 配额检测与用量归属

### 9.1 能拿到什么

- CodeBuddy 本地 `/api/v1/auth/account/status` 只返回 `authenticated + account`，**没有额度字段**；
- 因此 v1 不做主动余额查询，只做**被动识别 + 冷却**；
- 如果后续发现厂商有稳定的 usage / quota 接口，再加 `quota_remaining` 字段与 `quota_aware` 策略。

### 9.2 识别来源

1. **记录网关**（开启时）：
   - 状态码 `401/402/403/429`；
   - 错误体关键词：`quota / limit / exceeded / insufficient / credit / balance / 额度 / 积分 / 上限`；
   - 命中后写 `kernel_credential_members.state/cooldown_until/last_error`；如果是网关 Key，则写对应的网关 Key 状态。
2. **CLI 错误事件**（记录网关关闭时兜底）：
   - 适配器 `classify_failure(text, status)` 返回 `quota` / `auth`；
   - 运行层在收到错误事件时调用 `broker.report_failure()`。
3. **手动标记**：
   - UI 提供「停用 / 恢复 / 重置冷却」；
   - 适合用户明确知道某个账号已用完。

### 9.3 用量归属

- `UsageRecord.credential_member_id` 记录本次请求使用的成员；
- 记录网关在 `persist_usage()` 写入；
- 原生事件路径由运行层在写账本时带上 `ctx.credential_member_id`；
- 用量页增加「按成员」维度：请求数、token、成本、最近使用时间；
- 外部 API Key 仍用 `api_key_id`，不要和 `credential_member_id` 混用。

## 10. 安全

1. **API Key**：只存 `security.encrypt()` 后的密文；解密只在服务端内存；不写日志 / 事件 / 响应。
2. **OAuth slot**：`kernel_credential_members` 只存 `slot_ref`，blob 仍在适配器槽位目录（0600）；不在数据库复制。
3. **运行目录**：0700；凭据文件 0600；运行结束清理；崩溃残留由启动清扫 / TTL 清理。
4. **日志 / 轨迹**：复用现有 `scrub` / `_run_secrets`；新增字段不打印明文。
5. **回写**：先写临时文件再原子替换；覆盖前保留一份 `last_good` 备份（可选），避免坏 session 覆盖好 session。
6. **权限**：账号槽位是机器级资产，管理接口保持管理员权限；普通用户只看到「池可用 / 冷却中」，看不到密钥或昵称明细（按现有 `api/runtimes.py` 的约定）。
7. **审计**：记录谁在什么时候添加 / 删除 / 停用成员，以及手工恢复操作。

## 11. 兼容与迁移

### 11.1 不破坏现有行为

- 内核池 `enabled=false` 时，完全走现状：`bind_gateway()` / `activate_selected_account()` 不变；
- `AgentProfile.account_id` 保留：有值时视为「固定账号槽位」，优先于池；
- `activate_account()` 保留：手动切号、旧接口、旧前端继续可用；
- 现有 CodeBuddy 槽位不需要迁移：首次启用内核池时按槽位生成 `kernel_credential_members` 记录即可。

### 11.2 迁移步骤

1. 新表 `kernel_credential_pools` / `kernel_credential_members` 由 `create_all` 自动建；
2. `conversations` / `usage_records` 的新列登记到 `ADDITIVE_COLUMNS`；`Gateway` 不需要加池列；
3. 启动迁移（可选）：对已有槽位的内核（如 CodeBuddy），自动生成成员记录，但池 `enabled` 仍为 false；
4. 管理员在**内核管理**页手动开启池、调整策略；
5. 旧对话没有 `credential_member_id`，首次运行按策略选一个并写入（粘性）。

### 11.3 回滚

- 关闭内核池 `enabled` 即回到现状；
- 不删除成员数据，便于再次开启；
- 回写逻辑独立于选号，关闭池后不影响手动切号。

## 13. 测试计划

| 类别 | 用例 | 目标 |
| --- | --- | --- |
| 选号 | round_robin / LRU / weighted / failover / sticky | 公平、可复现、可注入 RNG |
| 健康 | 429 → cooling；到期恢复；401 → disabled | 状态机正确 |
| 租约 | 并发抢同一成员；过期回收；崩溃恢复 | 不串号、不死锁 |
| 物化 | CodeBuddy fake HOME；Codex `CODEX_HOME`；豆包数据目录 | env / 文件正确 |
| 回写 | fake CLI 修改 auth 文件；capture 写回槽位 | 刷新不丢 |
| 清理 | 正常结束 / 取消 / 异常 | 临时目录清理，权限正确 |
| 失败转移 | 首响应前 quota；已有输出后出错 | 该换则换，该停则停 |
| 用量 | 账本写入 `credential_member_id` | 可按成员汇总 |
| 安全 | 日志 / 事件 / 轨迹不含密钥 | 复用 scrub 断言 |
| 兼容 | 关闭池、固定 account_id、手动切号 | 零回归 |
| 跨平台 | Linux / macOS / Windows | HOME / USERPROFILE / junction |

**测试替身建议**：

- 写一个 fake `codebuddy` / `codex` 脚本，打印 `HOME` / `CODEX_HOME` 与 auth 文件路径，验证隔离；
- 不依赖真实厂商网络，避免测试消耗额度；
- 真实冒烟只用一个免费模型 / 测试账号，且默认不进 CI。

## 14. 风险与待决问题

### 14.1 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| refresh token 轮换 | 不回写会把槽位跑废 | `finally` 回写 + watcher + 每账号串行 |
| macOS Keychain | 复制目录不够 | Keychain 读写或 API Key 回退 |
| 豆包 `mssdk` 设备身份 | 登录态与设备身份分家，报安全存储不可用 | 槽位同时保存 `doubao_cli` + `mssdk` |
| Windows 路径 | `USERPROFILE` / junction / `.cmd` 垫片 | 单独真机测试；适配器集中处理 |
| HOME 副作用 | Bash 工具丢 git/ssh/npm 配置 | 符号链接农场，只隔离 auth 子树 |
| 内核更新 | auth 路径 / 文件格式变化 | 版本探测 + 冒烟测试 + 失败告警 |
| 厂商风控 | 账号被限 / 封 | 冷却、告警、审计；仅用于有权使用的账号 |
| 并发刷新 | 同一账号两个运行抢 refresh | 默认每账号并发 1；租约 |
| 后台任务 | 起标题 / 协作静默消耗池 | 默认排除或指定后台成员 |

### 14.2 已定与待决

**已定**：

- **账号槽位池挂内核**（按 `type_id`），同一内核的所有智能体共享；不挂网关；
- **API Key 池仍挂网关**，保持「网关是 API Key 唯一来源」的铁律。

**待决**：

1. **默认策略**：建议 `sticky + least_recently_used`；是否需要按用户可配？
2. **新账号是否自动入池**：建议登录后默认入池但 `enabled=true`，由管理员决定是否启用。
3. **后台任务策略**：起标题、协作是否参与轮询？建议默认不参与，或指定一个「后台成员」。
4. **Claude Code 的 v1 范围**：只做 API Key 池，还是一并做 OAuth 槽位？建议先 API Key。
5. **豆包的 v1 平台**：先 Linux/macOS，Windows 后置？
6. **普通用户能否使用管理员的池**：账号是机器级资产；建议管理员管理、普通用户只使用，不暴露账号明细。
7. **配额展示**：没有厂商余额接口时，是否允许用户手动填「每日额度 / 权重」？建议允许，作为 `weighted` 的依据。

## 17. 附录：可行性实测记录

> 记录时间：当前工作区。**不记录账号昵称、UID、token 或任何凭据内容。**

### 17.1 实验 1：临时 HOME 识别登录态

- 把当前 session 文件复制到临时目录：

```text
/tmp/xxx/.local/share/CodeBuddyExtension/Data/Public/auth/<auth-file>.info
```

- 用 `HOME=/tmp/xxx` 启动：

```bash
codebuddy --serve --host 127.0.0.1 --port <port> --auth none
```

- 请求：

```http
GET /api/v1/auth/account/status
x-codebuddy-request: 1
```

- 结果：`authenticated: true`，账号为目标账号。

### 17.2 实验 2：临时 HOME 完整运行

```bash
HOME=/tmp/xxx \
CODEBUDDY_CONFIG_DIR=/tmp/yyy \
codebuddy -p "Reply with exactly: OK" \
  --model hy4flash-free \
  --output-format json
```

- 结果：退出码 `0`，完整跑通；
- 使用的是 free 模型，没有消耗付费额度；
- 只带了 auth 文件 + 独立 config dir，说明 per-run HOME 的最小集成立。

### 17.3 结论

- CodeBuddy 的 auth 路径由 `os.homedir()` 决定，`CODEBUDDY_CONFIG_DIR` 不影响它；
- 同机复制 session 可用；
- per-run HOME + 独立 config dir 可以完整运行；
- 多账号只是把不同槽位的 blob 放进不同临时 HOME，机制一致。

### 17.4 清理

实验结束后已删除临时目录与脚本；没有在仓库或 `/tmp` 留下 session 副本。
