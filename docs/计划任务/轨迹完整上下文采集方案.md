## 0. 结论速览

| 决策点 | 结论 |
| --- | --- |
| 是否新增开关 | **不新增**。跟随现有 `users.trace_debug`，开关开即全采，关则零开销 |
| 采集入口 | 记录网关的转发层（`api/_forward.py`），这是 CLI 内核报文**唯一可见点** |
| 内核覆盖面 | 从 2 个（Claude Code / Codex）扩到 6 个（+ hermes / CodeBuddy / 两个 Harness） |
| 判定标准 | 从「有 `base_url_env`」改为「有 `Capabilities.recording_gateway`」 |
| 官方链路 | API Key 直连可覆盖；OAuth 走 passthrough；纯账号登录（豆包 / Antigravity）不可覆盖 |
| 体积上限 | 单事件 256 KiB → **2 MiB**；单会话 20 MiB → **100 MiB**；条数 2000 → 500 |
| 截断方式 | 从「JSON 文本切头尾」改为**结构感知裁剪**（保 `messages` 数组完整性） |
| 不可覆盖部分 | 轨迹如实标注「不可见」，**不伪造** |
| 新增依赖 | 无（MITM 方案暂不实施，见 §9） |

**一句话**：网关已经拿到了完整请求体，只是转完就扔了；把它脱敏后写进轨迹，就能补上 CLI 内核「真实发出去什么」这块长期空白。

## 1. 要解决什么问题

### 1.1 现状：轨迹只有「部分」上下文

轨迹功能（`docs/trace-debug-view-plan.md`）已实施，但采集精度分两层：

| 内核类型 | `request` 事件内容 | 能否看到真实上下文 |
| --- | --- | --- |
| API 内核（`openai_harness`） | 完整请求体 `body: payload` | ✅ 能 |
| CLI 内核（Claude Code / Codex / …） | 只有 argv、stdin、env 键名 | ❌ 看不到 |

CLI 内核的子进程自己组装模型请求，平台只记录「进程入参」和「原始输出」。前端 `lib/trace.ts` 为此专门写了「不可见环节」提示：

```typescript
export const INVISIBLE_SEGMENT_NOTE =
  '不可见环节：CLI 内核在子进程内部发起模型调用，真实 HTTP 请求体与响应体平台采集不到。'
```

### 1.2 为什么「部分」特别容易误导

`context_snapshot` 是**平台侧视角**的快照，不是内核实际发出的内容：

- system prompt 只存长度 + sha256 前缀（`trace.py:367-390`）
- 历史每条 ≤8 KiB、总量 ≤32 KiB（`trace.py:70-72`）

更关键的是：Claude Code / Codex 都是 `sessions=True`，用 `--resume` 自己维护内核侧会话（`claude_code.py:556`、`codex.py:327`）。**平台手里的 `ctx.history` 只是「平台以为内核发了什么」**，两者可能差很远。

排障时最需要回答的问题恰恰是「内核到底发了什么」，现在答不上来。

### 1.3 网关是唯一的可见点

记录网关（`runtime/recording_gateway.py`）转发时**完整持有请求体**：

```python
# api/usage_gateway.py:54
body=await request.body()
```

但这具请求体只喂给上游，**没有一个字进轨迹**。`api/_forward.py:3` 写得很直白：

> 只做**直通转发**：不改请求体、不做跨协议翻译、**不落正文**

`docs/usage-gateway.md:144` 同样声明「不记录请求 / 响应正文」。

**缺口就是这里**：网关是整条链路上唯一能亲眼看到 CLI 内核报文的地方，但它现在只记了账，没记内容。

## 2. 现状盘点：注入能力比以为的强

### 2.1 关键发现

改造前的判定逻辑（`service.py:282`）：

```python
if not definition.base_url_env:
    return None
```

这个判据**用环境变量当唯一标准**，误杀了两个已经写好注入代码的内核：

| 内核 | 注入方式 | 代码状态 | 能力声明 |
| --- | --- | --- | --- |
| Claude Code | env `ANTHROPIC_BASE_URL` | ✅ 已有 | ✅ 已声明 |
| Codex | 具名 provider | ✅ 已有 | ✅ 已声明 |
| **hermes** | 命令行 `--base-url` | ✅ **已有**（`hermes_agent.py:399`） | ❌ **没声明** |
| **CodeBuddy** | `models.json` 的 `url` | ✅ **已有**（`_sync_models_json`） | ❌ **没声明** |
| openai_harness | env `OPENAI_BASE_URL` | ✅ 已有 | ❌ 没声明 |
| deepseek_harness | env `DEEPSEEK_BASE_URL` | ✅ 已有 | ❌ 没声明 |
| 豆包 / Antigravity / Custom CLI | 无 | ❌ | — |

**四个内核的注入代码已经写好了，只差能力声明。**

### 2.2 hermes 的证据

```python
# hermes_agent.py:399-404 —— 网关注入早已实现
if ctx.gateway_url and ctx.api_key:
    argv += [
        "--provider", "custom",
        "--base-url", ctx.gateway_url,
        "--api-key", ctx.api_key,
    ]
```

注释还记录了实测结论：

> Hermes **没有**「换个端点」的环境变量：`OPENROUTER_BASE_URL` 它不读，
> 自定义端点只能走命令行（`--provider custom --base-url …`）。

**能力有，但 `base_url_env = None` 让它被判为「不支持」。**

### 2.3 CodeBuddy 的证据

```python
# codebuddy_cli.py:_sync_models_json —— 网关写入早已实现
base = ctx.gateway_url.rstrip("/")
url = base if base.endswith("/chat/completions") else f"{base}/chat/completions"
payload = {
    "models": [{
        "id": model_id,
        "url": url,
        "apiKey": "${CODEBUDDY_API_KEY}",   # 密钥不落盘
        ...
    }],
}
```

注释解释了为什么不用环境变量：

> 故意不声明 `CODEBUDDY_BASE_URL`：它会被内核拼成 `<base>/v2/chat/completions`，
> 与平台的 OpenAI 兼容网关语义不一致。

### 2.4 判定标准必须改

```
旧：有没有 base_url_env 环境变量
新：能不能把 base_url 写进它读的地方（环境变量 / 配置文件 / 命令行参数）
```

`Capabilities.recording_gateway` 这个字段本来就是为这件事设计的，只是注释把语义写窄了：

```python
#: 是否可接入记录网关：声明即表示该内核接受 ``base_url_env`` 覆盖……
recording_gateway: bool = False
```

**改造**：把注释语义放宽为「接受任意形式的 base_url 覆盖」，判定逻辑改读这个字段。

## 3. 外部参考：Ekko Studio 怎么做

Ekko Studio 是同类项目（Node 栈），它的做法验证了我们的方向，也划出了边界。

### 3.1 相同的架构

它的本地代理与我们的记录网关思路一致：

```typescript
// services/coding-agents/services/claude-code/proxy.ts
function localProxyBaseUrl(): string {
  return `http://127.0.0.1:${config.port}/api/ekko-studio/models`
}
```

回环地址 + 一次性 token + 注册表反查，与我们 `recording_gateway.proxy_base_url()` 同构。

### 3.2 它的核心手法：逐内核适配配置写入点

`docs/native-coding-agents.md` 明确写了每种内核的注入方式：

| Runtime | Scoped 配置方式 |
| --- | --- |
| Qwen | `QWEN_HOME` + modelProviders + 显式 auth/model 旗标 |
| Kimi | `KIMI_CODE_HOME` + 内存态 `KIMI_MODEL_*` 覆盖 |
| CodeBuddy | `CODEBUDDY_CONFIG_DIR` + **私有 models.json 别名** |
| Copilot | `COPILOT_HOME` + BYOK 环境变量 |
| ZCode | 显式 builtin/personal 配置文件 |

关键原则（原文）：

> The existing provider gateways translate all three Studio API modes
> (Chat Completions, Responses, Anthropic Messages). Upstream credentials stay
> in the server proxy; native runtime files contain only a local proxy token.
> **Proxy events record usage; native events own the chat/tool lifecycle to avoid
> duplicate messages or premature completion.**

最后半句正好点出我们 t7 要处理的「双记」问题。

### 3.3 它也没解决的部分

Ekko Studio 的 `PROVIDER_ENV_MAP` 里，这些 provider 的 `base_url_env` 是空的：

```typescript
'claude-oauth': { api_key_env: '', base_url_env: '' },
'xai-oauth':    { api_key_env: '', base_url_env: '' },
'minimax-oauth':{ api_key_env: '', base_url_env: '' },
'cliproxyapi':  { api_key_env: '', base_url_env: '' },
```

**纯 OAuth 账号登录型它同样走不通**，也没有 MITM。这印证了我们的判断：无注入缝的内核，两条代理路线都够不着。

## 4. 覆盖范围与边界

### 4.1 三层能力模型

| 层级 | 判定条件 | 覆盖内核 | 成本 |
| --- | --- | --- | --- |
| **L1 已有代码** | 注入代码已实现 | Claude Code、Codex、hermes、CodeBuddy、两个 Harness | 补声明即可 |
| **L2 官方 API Key** | 拆掉 `kind != "custom"` 闸门 | L1 中走官方 API Key 的 | 改一行判断 |
| **L3 官方 OAuth** | passthrough 模式 | Claude Code 订阅登录、Codex ChatGPT 登录 | 需实测 |
| **L4 无注入缝** | 无 | 豆包、Antigravity、Custom CLI | ❌ 不可达 |

### 4.2 明确不支持的部分

以下内核**没有可写入的 base_url**，网关原理上够不着：

- **豆包**：`base_url_env = None`，账号登录型，靠 `doubao login` 扫码
- **Antigravity**：`base_url_env = None`，官方脚本安装
- **Custom CLI**：`base_url_env = None`，用户自定义命令

轨迹里对这些内核**继续如实标注「不可见」**，绝不伪造内容。前端已有 `INVISIBLE_SEGMENT_NOTE` 机制，保留。

### 4.3 一个容易搞错的点：CodeBuddy 的协议错配

```python
# codebuddy_cli.py
protocol = "openai"                    # 请求协议：OpenAI Chat
usage_protocol = PROTOCOL_ANTHROPIC    # 响应 usage 形状：Anthropic
```

**请求协议与 usage 协议不同**。网关注册时 `provider=gateway.protocol` 用的是请求协议，但账本归一化要按 `usage_protocol`。实施时不要用错，否则缓存 token 会算重。

## 5. 架构设计

### 5.1 数据流

```text
CLI 子进程
   │  base_url 指向代理（env / 配置文件 / 命令行，逐内核不同）
   ▼
/api/internal/usage-gateway/<token>/...
   │
   ├─► 【新增】body 脱敏 → 写一条 request 轨迹（transport=gateway）
   │
   ▼
上游真实网关
   │  响应流
   ▼
   ├─► tee 解析 usage → 写账本（现有逻辑，不动）
   └─► 【新增】响应脱敏 → 写一条 response 轨迹
```

### 5.2 关联关系怎么建立

网关路由是**无状态**的（只有 token），拿不到 `ctx`。但 `ProxyTarget` 上已经带齐了关联键：

```python
# recording_gateway.py:72-96
@dataclass(slots=True)
class ProxyTarget:
    token: str
    run_id: str
    owner_id: str | None = None
    conversation_id: str | None = None
    agent_type_id: str = ""
    agent_profile_id: str | None = None
    ...
```

**问题**：`ActiveRun` 上没有 `trace` 字段（`manager.py:15-48`），查不到采集器。

**解法**：

1. 给 `ActiveRun` 加一个 `trace` 字段
2. `_start_trace` 建好采集器后挂上去
3. 转发时用 `registry.get(target.run_id)` 反查

### 5.3 时序没问题

`prepare_run` 里的顺序是：

```python
# service.py:706 网关注册
_apply_recording_gateway(ctx, _recording_gateway_binding(...))
# service.py:713 轨迹采集器创建
trace = await _start_trace(...)
```

网关注册**早于**轨迹创建，但注册只是往注册表塞目标，**真正的转发发生在子进程发请求时**——那时 recorder 早已就位。所以时序是安全的。

### 5.4 双记防护

`openai_harness` 是 `Runtime.API`，自己已经在写轨迹：

```python
# openai_harness.py:283-295
await trace.request({"transport": "http", ..., "body": payload})
```

如果它也走网关（`CODA_RECORDING_GATEWAY=on`），会记两份。

**解法**：`ProxyTarget` 加 `capture_trace: bool`，注册时按内核 Runtime 判定：

```python
capture_trace = definition.runtime is Runtime.CLI
```

只给 CLI 内核补，API 内核跳过（它自己的采集已经更完整）。

### 5.5 外部网关天然安全

`api/model_gateway.py` 构造 target 时 `run_id = f"ext:{key.id}:..."`，`conversation_id=None`。反查不到 run 就跳过，不会误采。

## 6. 体积与截断策略

### 6.1 现有上限

```python
# trace.py:60-72
MAX_EVENT_BYTES = 256 * 1024          # 单事件
MAX_EVENTS_PER_CONV = 2000            # 单会话条数
MAX_CONV_BYTES = 20 * 1024 * 1024     # 单会话总量
_HISTORY_ENTRY_BYTES = 8 * 1024       # 历史单条
_HISTORY_TOTAL_BYTES = 32 * 1024      # 历史总量
```

完整上下文动辄几十到几百 KB，256 KiB 刚好卡脖子，20 MiB 几轮就见底。

### 6.2 新上限

| 项 | 旧值 | 新值 | 理由 |
| --- | --- | --- | --- |
| 单事件 | 256 KiB | **2 MiB** | 容纳大多数完整上下文 |
| 单会话总量 | 20 MiB | **100 MiB** | 配合 2 MiB 单事件 |
| 单会话条数 | 2000 | **500** | 与总量反向调整，避免条数先耗尽 |

**为什么条数要降**：2 MiB × 2000 = 4 GiB，远超总量上限。不降条数的话，`MAX_EVENTS_PER_CONV` 永远不触发，实际由 `MAX_CONV_BYTES` 控制，两个参数失去平衡。降到 500 后，两者大致同步。

### 6.3 截断方式必须重写

现在的实现是**对 JSON 文本切头尾**：

```python
# trace.py:168-178
def _truncate_payload(payload: dict[str, Any]) -> dict[str, Any]:
    raw = json.dumps(payload, ensure_ascii=False, default=str).encode("utf-8")
    head = raw[:_TRUNCATE_HEAD_BYTES].decode("utf-8", "ignore")
    tail = raw[-_TRUNCATE_TAIL_BYTES:].decode("utf-8", "ignore")
    return {"__truncated__": True, "head": head, "tail": tail, ...}
```

截完是一堆残缺字符串，`json.loads` 都过不了。

**新实现：结构感知裁剪**

```python
def _truncate_payload(payload):
    # 1. 若含 messages 数组：逐条保留结构，只对单条超长 content 截断
    # 2. 丢弃最早的消息，直到体积达标（保留 system + 最后 N 轮）
    # 3. 标记 truncated=True + 记录丢弃条数
```

原则：**宁可少几条消息，不要给出乱码**。排障时「少了第 3 轮」比「整个 JSON 坏了」有用得多。

## 8. 安全设计

### 8.1 脱敏复用现有机制

不要另写一套。`trace.sanitize()` 已经处理：

- 凭据值擦除（`credentials.scrub`）
- 敏感键掩码（`authorization` / `cookie` / `api_key` / `token` / `secret` 等）
- 内联二进制替换（base64 图片只留引用与大小）

网关报文直接套用：

```python
safe_body, redacted = sanitize(body, secrets=recorder_secrets)
```

### 8.2 一个现有漏洞要顺手补

```python
# api/_forward.py:103
return Response(content=_scrub_secret(raw, target.api_key), ...)
```

只擦 `target.api_key`。但 **passthrough 模式下它是 `None`**（官方 OAuth 不注入密钥），上游错误体可能把用户自己的 OAuth 令牌回显给前端。

**修复**：passthrough 时从请求头提取凭据值，一并加入擦除列表。

### 8.3 隐私边界

- 正文只进轨迹表，不进消息表、不进日志
- 轨迹接口是 `require_owned_strict`，管理员也不豁免（见 `AGENTS.md` 多用户归属条款）
- 用户关闭 `trace_debug` 后，不采集、不写库、零开销

## 9. MITM 方案评估（暂不实施）

### 9.1 为什么考虑它

反向代理要求「内核愿意改 base_url」。没有注入缝的内核（豆包 / Antigravity）只能靠正向代理 + MITM，从网络层截获。

### 9.2 项目现状

`egress.py` 已经有正向代理的雏形：

```python
_PROXY_ENV_KEYS = ("HTTP_PROXY", "HTTPS_PROXY", "ALL_PROXY", ...)

def proxy_env_for_subprocess() -> dict[str, str]:
    if egress_mode() == "off":
        return {}
    return {key: _BLACKHOLE_PROXY for key in _PROXY_ENV_KEYS}
```

现在指向黑洞端口（`127.0.0.1:9`）用来**阻断**。换成真代理就从「阻断」变「抓包」，注入点 `runner.py:250` 覆盖所有 CLI 内核。

**但项目里没有任何 MITM 底座**（无证书生成、无 CA 注入、无 CONNECT 隧道处理），要从零建。

### 9.3 代价评估

| 要解决的问题 | 难度 |
| --- | --- |
| 生成 CA 证书 + 动态签发服务端证书 | 中 |
| 让 Node 内核信任自签 CA（`NODE_EXTRA_CA_CERTS`） | 中 |
| 让 Python / Go 内核信任（`SSL_CERT_FILE` / `REQUESTS_CA_BUNDLE`） | 中 |
| 处理证书固定（pinning） | **高，可能无解** |
| CONNECT 隧道 + SSE 流式转发 | 高 |

额外风险：很多 CLI 不读 `HTTP_PROXY`。Node 的 `fetch`（undici）默认不走代理，需要额外配置。

### 9.4 结论

**暂不实施。** 理由：

1. L1–L3 已覆盖主力内核（Claude Code / Codex / hermes / CodeBuddy）
2. MITM 是独立项目，引入「平台持有可解密所有流量的 CA」这种高敏感资产
3. 即使做了也可能被 pinning 挡住，投入产出比不确定

**建议**：先做 L1–L3，观察实际排障需求。若确有大量「看不到」的抱怨，再单独立项做可行性验证（t11 只做验证，不进主分支）。

## 10. 验收标准

### 10.1 功能验收

| 场景 | 预期 |
| --- | --- |
| Claude Code + 自定义网关 + 开启轨迹 | 轨迹里能看到完整 `messages[]` |
| hermes + 自定义网关 + 开启轨迹 | 同上（补声明后） |
| CodeBuddy + 自定义网关 + 开启轨迹 | 同上（补声明后） |
| openai_harness | 不重复记（它自己有） |
| 豆包 / Antigravity | 显示「不可见」，不伪造 |
| 关闭 `trace_debug` | 无任何轨迹写入，无性能开销 |
| 外部 API 调用 | 不写轨迹（`conversation_id=None`） |

### 10.2 安全验收

- 网关报文里的 `Authorization` / `x-api-key` 必须是 `***`
- 凭据值（用户配置的密钥）不得出现在轨迹里
- passthrough 模式下 OAuth 令牌不得回显

### 10.3 体积验收

- 超大上下文（>2 MiB）被裁剪后仍是合法 JSON
- `truncated=true` 且能看到丢弃条数
- 单会话达到 100 MiB 后按 `created_at` 从旧到新裁剪

## 11. 风险与回退

| 风险 | 缓解 |
| --- | --- |
| 100 MiB 让数据库明显变大 | 可配置化；默认值可按部署调低 |
| 结构感知裁剪逻辑有 bug | 保留原始 `_truncate_payload` 作为兜底路径 |
| 官方 OAuth 实测失败 | t9/t10 独立提交，失败可单独回退 |
| 某些内核补声明后行为异常 | 能力声明只影响 `auto` 模式，可逐个开关 |

**回退策略**：全部改动在 `CODA_RECORDING_GATEWAY=off`（默认值）下不生效，出问题关开关即可。
