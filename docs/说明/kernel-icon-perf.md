# 内核图标加载耗时：验证记录

工单：优化内核管理页图标加载为秒显（Windows 端）

## 怎么测的

- 机器：本仓库开发机（Linux，容器），Chromium 156 headless。
- 后端：真后端（`uvicorn app.main:app`，关鉴权）跑在本机 8011 端口，前端用 `npm run build`
  的产物（`frontend/dist`）。
- 路径：每次都从「设置」页重新点进「内核管理」标签页（`/settings` → 点「内核管理」），
  与真实用户路径一致。
- 口径：**页面可见（点下标签页那一刻）→ 全部图标显示完成**。
  「显示完成」= 图标资源全部取回 + 浏览器画完两帧（第一帧画图标，第二帧确认已上屏）。
  计时用 epoch 毫秒，页面侧与 CDP 网络事件换算到同一时钟。
- 工具：`node scripts/measure_kernel_icons.mjs <地址> 10`（零依赖，CDP 驱动 headless Chromium）。
- 页内埋点：`window.__kernelLogoPerf`（`frontend/src/lib/kernelIcons.ts`），另记内核列表接口
  耗时，便于把「接口慢」和「图标慢」分开看。

## 为什么改动前这么慢（根因）

CDP 网络事件抓到的请求时间线（改动前）：

```
接口 runtimes     起=4863 回=24   完=24      ← 内核列表接口本身很快
接口 check        起=4892 回=1523 完=1522    ← 管理员「检查更新」的 npm view
接口 check        起=4889 回=1658 完=1659
图标 deepseek.svg 起=4901 回=1656 完=1657   ← 图标请求排在 check 后面
图标 claude.svg   起=4901 回=1682 完=1682
图标 doubao.png   起=4909 回=1704 完=1704
```

两条原因叠加：

1. **图标走外部路径**：由后端的 SPA 兜底路由返回（`Cache-Control: no-cache`），每次进页面
   都要重新校验一遍（条件请求 + 往返）。
2. **请求排队**：管理员的「检查更新」是每个内核一次 `npm view` 远端查询（各约 1.5～2.3 秒），
   把浏览器每域名的连接数占满；图标请求排在它们后面，于是要等 1.7～2.8 秒才画出来。

改动后图标是构建期内嵌进前端包的 data URL：零请求、零排队，页面一渲染就画出来。
剩下的耗时是内核列表接口（约 20～40ms）与浏览器绘制。
